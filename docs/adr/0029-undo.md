# ADR 0029: Run journal and Undo

Status: Implemented for local and SFTP folders

## Context

PLAN.md §3.8 promises a completion card with Undo: "created files go to
the archive; deleted and overwritten files come back from it. Anything it
can't reverse is listed." Runs recover from crashes without a journal
([ADR 0020](0020-run-execution.md)), so nothing recorded what a finished
run wrote.

## Decision

**Journal.** Each run records every write it makes — create, replace,
metadata update, archive — with the path, the side written, the version
it left (or, for an archive, the version it moved away) and the path's
base before the run. Entries are committed in the same transaction as the
base updates of those writes (state schema v15, `run_journal`). A run's
first recorded batch replaces the previous run's entries, so the journal
always describes the pair's newest run that wrote anything. Changing a
pair's roots or metadata categories discards it, like the base.

**Undo** (`sync.undo`, `foldover sync ID --undo`, the app's Undo button)
observes both folders, then walks the journal backwards:

| The run had | Undo, while the path still holds what the run left |
|---|---|
| created an entry | moves it to the undo's own archive folder |
| replaced an entry | archives the newer one, puts the earlier one back |
| archived an entry | puts it back from the run's archive |
| updated metadata | nothing: earlier metadata is not kept |

```text
journal (write order)          undo (reverse order)
0 create  photos/              4 put back  old/notes.txt
1 create  photos/a.jpg         3 put back  report.txt, after archiving
2 meta    readme.md              what replaced it
3 replace report.txt           2 listed: earlier metadata is not kept
4 archive old/notes.txt        1 archive   photos/a.jpg
                               0 remove    photos/ (empty again)
```

- An entry that changed since the run, an earlier version already pruned
  from the archive, or a folder that is no longer empty is left as it is
  and listed with the reason. A put-back that finds its path taken goes
  beside it as `name (restored).ext`. If the earlier version of a
  replacement is missing, the newer one is put back where it was.
- A removed folder comes back with the first file put back inside it;
  empty folders are not recreated.
- Undone paths get their base from before the run, so the next preview
  shows exactly what syncing again would redo. Each batch of up to 256
  entries is judged from the fresh observation first; the base restores
  of the entries about to be reverted commit before any file changes. A
  crash in between leaves those paths as the run left them under their
  pre-run base, where the next run finds both sides equal (or a conflict)
  and writes nothing; undoing again finishes the job.
- The first such commit also holds the pair (`automation_hold`): unattended
  runs skip it, across crashes and restarts, until a person's sync
  actually runs. An undo that fails before changing anything holds
  nothing; a person's sync that stops before running releases nothing.
  The pair's status becomes `undone`.
- A finished undo spends the journal; a cancelled one keeps it, so undoing
  again continues. History records the undo with trigger `undo`
  (`archived`: entries removed, `recovered`: entries put back).
- Undo changes only the side the run wrote. Changes a person made in the
  other folder are theirs and stay; the redo preview offers them again.

## Consequences

- The journal costs one row per write of the newest run, about the size
  of a base row; a first sync of a million files stores a million rows
  until the next writing run replaces them.
- Older agents cannot read schema v15 (minimum reader 15): they would keep
  a stale journal and cannot decode undo history rows.
- After an agent restart the app shows a held pair as ready and offers
  no Undo until the next sync, though `foldover sync ID --undo` still
  works; automatic syncs keep waiting for the person's next sync.
- SFTP put-back checks the destination, then renames; a file created at
  that path in between can be replaced (ADR 0028's trusted-server model).
- Only the newest writing run can be undone; undoing an older one would
  need every later run's journal and is out of scope.
- Crash recovery stays journal-free (ADR 0020); the journal serves Undo.
