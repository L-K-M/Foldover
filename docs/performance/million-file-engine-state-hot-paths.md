# Performance proposals: engine and state-store hot paths for million-file SFTP syncs

Foldover is a macOS app over a portable Rust engine (`crates/`): `foldover-service` schedules jobs, `foldover-engine` loads a SQLite-backed base and both sides' snapshots, observes the endpoints, plans against the base, then applies copies, metadata updates, moves and archives on a worker pool while the run thread journals every write and commits base/journal rows in batches of 256 (`COMMIT_BATCH`, `crates/foldover-engine/src/run.rs:52`). The workload studied here is comparing and copying millions of documents to an SFTP server on the local network; the primary metric is end-to-end wall-clock time of a sync/backup run. Six sibling documents in this directory already cover the SFTP wire path (read-window sizing, observe/copy round trips, listing parallelism, stat-trust re-observation, local scan syscalls, per-file request counts). This document is the engine/state-store complement: it covers the work the SFTP passes do not name, including the base and snapshot lifecycle, the SQLite write path, the planner's use of the base, and the engine lock. Proposals are ranked by expected reduction in end-to-end time weighted by effort and risk. Code facts and line numbers were read in the source at the current checkout; the only live measurement taken in this pass is the SQLite journal-cleanup query plan and timing reported below, and everything else is labelled as a hypothesis, not a guarantee.

## Ranked proposals

1. Stop the per-batch journal delete from scanning the run's own journal
2. Store a post-write snapshot so the next run does not re-read what Foldover just wrote
3. Batch snapshot writes with a temp table instead of per-row statements
4. Plan over borrowed observations instead of cloning every version
5. Overlap the base load with the side observations and shorten the engine-lock hold
6. Validate tree parents during the sorted merge instead of three full passes
7. Compact the SFTP session's per-request bookkeeping
8. Add a release profile with thin LTO and one codegen unit

## Measured in this pass

The per-batch journal cleanup is the one item below backed by a live measurement rather than code reading. The schema is `PRIMARY KEY (pair_id, run, seq)` on `run_journal` (`crates/foldover-db/src/database.rs:203-215`), and `journal::apply` executes `DELETE FROM run_journal WHERE pair_id=?1 AND run!=?2` on every `JournalChange::Record` (`crates/foldover-db/src/database/journal.rs:83-86`), which the engine sends once per 256-row batch (`crates/foldover-engine/src/run.rs:1177-1187`, `crates/foldover-engine/src/configuration.rs:438-450`).

- `EXPLAIN QUERY PLAN DELETE FROM run_journal WHERE pair_id=?1 AND run!=?2` on a table with that exact schema returns `SEARCH run_journal USING PRIMARY KEY (pair_id=?)` (SQLite 3.54.0, macOS): the predicate cannot seek on `run`, so every batch scans every journal row of the pair.
- Isolated scan cost (Python 3 `sqlite3`, a `WITHOUT ROWID` table with the same primary key, one `DELETE` per 256-row batch, no commits during the loop): 100,000 rows = 2.46 s, 200,000 = 9.57 s, 400,000 = 38.99 s, 800,000 = 249.17 s. The growth is quadratic.
- The same loop with the production pragmas (`WAL`, `synchronous=FULL`, commit per batch) gives 50,000 = 1.75 s, 100,000 = 3.60 s, 200,000 = 12.24 s; the fsyncs dominate at small sizes and the scan term dominates at large sizes.

Extrapolating the measured quadratic coefficient to one million rows gives roughly 250-390 s of pure SQLite scan work per run. That extrapolation is a hypothesis from the measured coefficient, not a measurement; the fix in proposal 1 removes the term entirely.

## 1. Stop the per-batch journal delete from scanning the run's own journal

- **Category:** algorithmic complexity
- **Evidence:** `crates/foldover-db/src/database/journal.rs:50-110` (`JournalChange::Record` runs the `DELETE` at lines 83-86 on every batch); `crates/foldover-engine/src/run.rs:52` (`COMMIT_BATCH = 256`), `:1177-1187` (`commit_batch` closure), `:1616-1625` (`Executor.written`/`journal`); `crates/foldover-engine/src/configuration.rs:438-450` (`commit_run` maps every `Commit::Base` to `JournalUpdate::Record`); `crates/foldover-state/src/pairs/journal.rs:85-100`; schema `crates/foldover-db/src/database.rs:203-215`. The measured query plan and timing are in the previous section. The sibling document [sftp-million-file-db-apply-hot-paths.md](sftp-million-file-db-apply-hot-paths.md) proposal 1 inferred the same scan from the schema; this entry adds the measured plan and timing.
- **Hypothesis:** the delete exists to replace the previous run's journal on the first batch of a new run, but it runs on every batch. After the first batch the table contains only the current run's rows, so each later batch scans the whole journal to delete nothing. For a run that writes one million rows in 3,906 batches, that is the quadratic term measured above, on the run thread, while copy workers wait for the next batch.
- **Proposed change:** tell the store which batch begins a run. Add a `first: bool` to `Commit::Base` (`crates/foldover-engine/src/run.rs:180-184`), set it from a new `Executor.first_batch` flag (or `executor.written == executor.journal.len()` at commit time), pass it through `JournalUpdate::Record` and `JournalChange::Record` (`crates/foldover-state/src/pairs/journal.rs:85-100`, `crates/foldover-db/src/database/journal.rs:50`), and execute the delete only when `first` is true. The first batch of a run still removes the previous run's entries, preserving the documented "a run's first recorded batch replaces the previous run's entries" semantics. A schema-free `SELECT run FROM run_journal WHERE pair_id=?1 LIMIT 1` check is an acceptable alternative, but the explicit flag has no mixed-run edge case.
- **Expected impact:** removes the quadratic term from every write-heavy run. The measured scan component is roughly 250-390 s at one million writes on this host (extrapolated; confidence medium-high); even at five times faster on the production WAL/FULL setup it is minutes. Confidence: **high** on the mechanism (measured plan and scaling), **medium-high** on the magnitude.
- **Effort and risk:** small; blast radius is the journal table's cleanup. Risk: a wrong `first` flag could leave a previous run's journal rows, breaking `Database::journal`'s `max(run)` selection (`crates/foldover-db/src/database/journal.rs:113-117`); the existing tests there cover run replacement and spending, and the flag is set once per run by the executor.
- **Measurement plan:** add a Criterion bench `db_commit_batches_100k` that calls `update_base` 390 times with 256 changes each (the real batch shape) and times the loop; compare before/after. The existing `db_commit_100k` bench commits all 100,000 rows in one transaction and therefore does not exercise this path. End-to-end: run a 100k-file sync against the fixture `sftp-server` and compare apply-phase wall clock.

## 2. Store a post-write snapshot so the next run does not re-read what Foldover just wrote

- **Category:** redundant work and caching
- **Evidence:** `crates/foldover-service/src/sync.rs:905-917` stores both sides' snapshots after `PairRun::prepare` and before the `work` match, so the stored snapshot is the pre-run observation; `crates/foldover-engine/src/run.rs:997` (`execute(self, ...)`) consumes the run, so `PairRun::snapshot` (`run.rs:925-945`) cannot be called after the writes. `crates/foldover-endpoint/src/sftp.rs:631-659` (`observe_entry`) and `crates/foldover-endpoint/src/local.rs:1198-1204` reuse a stored entry only when the stored fingerprint still matches the current stat (SFTP) or `Fingerprint::proves_unchanged` holds (local). After a run writes a file, the stored fingerprint is the pre-write one (or the path is absent for a create), so the next run re-reads or re-hashes that file and rewrites its snapshot row. No sibling document proposes updating the snapshot from the writes.
- **Hypothesis:** after a first sync of one million files to SFTP, the next run re-reads all one million destination files (the pre-run snapshot has no entries for them) and rewrites all one million snapshot rows, even though Foldover just wrote them and knows their versions. The write path already fetches post-write attributes for verification (`staged_version_on` at `crates/foldover-endpoint/src/sftp.rs:921-935`, the local `receive_file` metadata), so the information needed to build a correct post-write fingerprint is available at write time. Without SFTP stat-trust, the local side still skips re-hashing written files (its `proves_unchanged` check), and the SFTP side saves the snapshot rewrite; with stat-trust (a sibling proposal that needs approval), the SFTP side also skips the re-read.
- **Proposed change:** have each endpoint record the post-write `ObservedEntry` (version, endpoint fingerprint key, size, observed time) as it verifies a write. Concretely: extend the `Endpoint` write methods (`copy_from`, `update_metadata_from`, `remove`, `move_entry`, `recover_leftover` in `crates/foldover-endpoint/src/endpoint.rs:325-410`) to return the post-write stat key they already fetched, or have the endpoint keep a per-run `Mutex<HashMap<SyncPath, ObservedEntry>>`; merge those entries into the snapshot after `execute` and drop entries for archived/deleted paths, then store the snapshot once. For local roots the fingerprint is `EntryMetadata::stat_key()`; for SFTP it is `stat_key(&attributes)` (`crates/foldover-endpoint/src/sftp.rs:1735-1745`). Keep the pre-run snapshot as a fallback when an endpoint cannot supply a post-write stat.
- **Expected impact:** removes one full re-read/re-hash of the written set after every run. For a one-million-file first sync followed by a no-change run, the second run's local observe drops by the written-file hash cost (measured elsewhere in this directory at about 109 µs/file) and its SFTP observe drops from a full corpus read to a listing under stat-trust; even without stat-trust, the snapshot rewrite drops from one million rows to near zero (the `db_snapshot_rewrite_100k` budget is 1000 ms per 100k). Confidence: **medium-high** on the mechanism, **medium** on the magnitude (depends on the direction and on whether stat-trust ships).
- **Effort and risk:** medium-high; it touches the `Endpoint` trait across local, SFTP, peer and simulation endpoints and the engine's executor. Risk: a wrong post-write fingerprint could make the next run trust a stale version. The stat-trust check compares the stored key to the current stat, so a wrong key fails safe (a mismatch forces a re-read); the dangerous case is a key that matches a later edit, which is the same stat-trust tradeoff the sibling documents already flag. Keep the pre-run snapshot for paths the write path cannot describe.
- **Measurement plan:** after a 100k-file first sync to the fixture `sftp-server`, time the second `observe_from` and count `READ` requests/bytes and `replace_snapshot` row updates, before and after. Existing regression gates: `crates/foldover-engine/src/run/tests/simulation.rs` and `crates/foldover-endpoint/src/sftp/tests.rs`.

## 3. Batch snapshot writes with a temp table instead of per-row statements

- **Category:** I/O and batching
- **Evidence:** `crates/foldover-db/src/database.rs:806-882` (`replace_snapshot`) computes `removed`, `added` and `changed` lists and then executes one `DELETE`, one `INSERT` and one `UPDATE` per row (lines 862-880). `crates/foldover-state/src/pairs.rs:276-296` builds a `Vec<SnapshotRow>` first. The `db_snapshot_rewrite_100k` budget is 1000 ms per 100k rows (`perf/budgets.toml`), and a sibling pass measured 192 ms for 100k on this host, so a full one-million-row rewrite costs about 2 s of per-row statement execution. Proposal 2 reduces how often a full rewrite happens, but a run that changes many files still pays it.
- **Hypothesis:** the per-row statements are the cost, not the data. A temp table plus set-based `DELETE`/`UPDATE ... FROM`/`INSERT ... SELECT` moves the same rows with a few statements and lets SQLite do the merge in C. The bundled SQLite (libsqlite3-sys 0.38.2) supports `UPDATE ... FROM` (3.33+) and `INSERT ... ON CONFLICT`.
- **Proposed change:** in `replace_snapshot`, create a temp table `incoming(pair_id, side, path, fingerprint, version)`, `executemany` the incoming rows into it, index it by `path`, then: delete stored rows whose path is not in `incoming`; update stored rows that differ; insert rows that are new. Keep the same transaction, revision check and `Dirty`/cache semantics, and keep the public `SnapshotRow` API for the non-bulk callers if needed. The sibling [sftp-million-file-db-apply-hot-paths.md](sftp-million-file-db-apply-hot-paths.md) proposal 4 avoids the unchanged case entirely; this entry covers the changed case.
- **Expected impact:** reduces a one-million-row snapshot rewrite from seconds to a small fraction of a second (medium confidence; the exact factor depends on SQLite's temp-table overhead and page cache). For a run that rewrites a large snapshot, this is a few seconds off the apply phase.
- **Effort and risk:** medium; the merge semantics (path order, changed detection, unchanged rows left alone) must be preserved exactly. Risk: a set-based `UPDATE ... FROM` or anti-join that misses a case; the existing `db_snapshot_rewrite_100k` and `db_snapshot_unchanged_100k` benches and the snapshot tests are the gate.
- **Measurement plan:** run `cargo xtask bench-check` (`db_snapshot_rewrite_100k`, `db_snapshot_unchanged_100k`) before/after and add a one-million-row variant; compare wall time and peak memory. End-to-end: time a run that changes 100k files and stores the snapshot.

## 4. Plan over borrowed observations instead of cloning every version

- **Category:** allocation and memory layout
- **Evidence:** `crates/foldover-endpoint/src/local.rs:584-590` (`Observation::versions`) builds a fresh `BTreeMap<SyncPath, EntryVersion>` per side per run; `crates/foldover-engine/src/run.rs:864-868` calls it for both sides before `plan_resolved`; `crates/foldover-engine/src/plan.rs:507-525` (`plan_resolved`) takes `&BTreeMap<SyncPath, EntryVersion>`. `EntryVersion` is 65 bytes (`crates/foldover-types/src/reconcile.rs:58-61`) and `SyncPath` owns a `Vec<u8>` (`crates/foldover-types/src/sync_path.rs:11`).
- **Hypothesis:** for a one-million-entry side, `versions()` allocates roughly one million `SyncPath` clones plus a new `BTreeMap`, on the order of 150-250 MB and hundreds of milliseconds per side, purely to hand the planner a read-only view it could take by reference. The planner only needs `Copy` `EntryVersion` lookups.
- **Proposed change:** add a planning entry point that takes `&BTreeMap<SyncPath, ObservedEntry>` (or a borrowed `Observation`) and uses `.map(ObservedEntry::version)` at the lookup sites; keep `plan_candidates`/`plan_resolved` for the existing tests and bench, or change their signatures and update the tests, the property tests and `crates/foldover-engine/benches/plan.rs`. The base tree can stay as-is.
- **Expected impact:** saves two full-tree clones per run (about 300-500 MB of peak allocation and 0.5-1.5 s of CPU at one million entries per side, medium confidence; the exact figure depends on path lengths and the allocator). It also lowers the plan phase's memory high-water mark, which matters for the 500 MB budget in PLAN.md §5.3.
- **Effort and risk:** medium; the planner's public signature is used by tests, the property tests and the bench. Risk is low (a read-only change); the plan's decision logic is unchanged and the existing plan tests and proptests cover equivalence.
- **Measurement plan:** run `plan_100k_entries` and a new one-million-entry variant with a counting `#[global_allocator]` before/after; measure peak RSS during `PairRun::prepare`. `cargo xtask bench-check` guards the plan budget.

## 5. Overlap the base load with the side observations and shorten the engine-lock hold

- **Category:** concurrency and parallelism
- **Evidence:** `crates/foldover-service/src/sync.rs:854-860` calls `engine.run_inputs(id)` while holding `engine.lock()`; `crates/foldover-engine/src/configuration.rs:242-263` (`run_inputs`) reads the base (`self.pairs.base(id)?`) and both snapshots from SQLite and decodes them into `BTreeMap`s before returning. `PairRun::prepare` (`crates/foldover-engine/src/run.rs:696-712`) needs the snapshots for the scan but needs the base only for planning after the scan. The doc comment on `run_inputs` says "for work outside the engine lock", but the only production caller holds the lock.
- **Hypothesis:** for a one-million-entry pair, the base read and decode (the `db_read_100k` budget is 300 ms, so about 3 s at one million) blocks every other pair's job and every status request while it runs, and it is serialized before the scan even starts. Loading the base concurrently with the scan hides it: the scan of a million local files is seconds to minutes, and the scan of an SFTP tree is longer still.
- **Proposed change:** split `RunInputs` into scan inputs (pair config, identities, resolutions, snapshots, reach, lease timing) and the base. Load the scan inputs under a short engine-lock hold, start `PairRun::prepare_on`'s observations, and load the base on a helper thread (or a `OnceCell`/`mpsc` joined before planning). Keep the revision check and the "a stale revision means the plan was built for other roots" semantics unchanged. If the base load fails, fail the run before planning, as today.
- **Expected impact:** hides the base read/decode behind the scan (a few seconds per million entries, low-medium confidence) and removes a multi-second engine-lock stall that blocks status requests and other pairs. The end-to-end gain for a single pair is the hidden load time; the responsiveness gain for the agent is larger.
- **Effort and risk:** medium; it restructures `RunInputs`/`prepare` and the service's job setup. Risk: the base must be consistent with the pair revision; the existing revision check at commit time still catches a mid-run config change, but the plan must not be built against a base that changed after the scan. Loading the base from the same SQLite connection under the same revision guard preserves today's semantics.
- **Measurement plan:** time `PairRun::prepare` on a pair with a one-million-entry base and a fixture SFTP tree, before and after; instrument the engine-lock hold time and the base-load time separately. Verify with `crates/foldover-engine/src/run/tests.rs` and the simulation suite.

## 6. Validate tree parents during the sorted merge instead of three full passes

- **Category:** algorithmic complexity
- **Evidence:** `crates/foldover-engine/src/plan.rs:523-525` calls `validate_tree` on the base, left and right trees before the merge; `validate_tree` (`plan.rs:714-733`) does a `BTreeMap` lookup for every entry's parent. The merge loop (`plan.rs:527-597`) then walks the same paths in sorted order. `plan_100k_entries` is budgeted at 350 ms and measured at 58.6 ms on this host (sibling pass), so the three passes are a measurable fraction of planning.
- **Hypothesis:** the trees are sorted, so a parent always precedes its children; a single incremental pass can validate each tree in O(n) with a stack of open directories instead of three O(n log n) lookup passes. The merge loop already builds a `directories` map (`plan.rs:532-540`) for the blocked-ancestor pass, so the information is available.
- **Proposed change:** replace the three `validate_tree` calls with an incremental check inside the merge: maintain a stack of `(path, is_directory)` per tree (or one stack with a tree tag); when a path is popped down to its parent, check that the parent is a directory. Preserve the exact error variants (`MissingParent`, `NonDirectoryParent`) and their tree roles, and keep the cancellation checks. The merge already iterates all three trees in order, so no extra pass is needed.
- **Expected impact:** removes about three million `BTreeMap` lookups at one million entries (a few hundred milliseconds, low-medium confidence). Planning is CPU-only and usually secondary to SFTP I/O, so the end-to-end effect is small.
- **Effort and risk:** small-medium; the error semantics and the order in which the three trees are validated must not change (the current code validates base, then left, then right). Risk: a subtle ordering change could report a different tree's error first; the plan tests cover `MissingParent`/`NonDirectoryParent`.
- **Measurement plan:** run `plan_100k_entries` before/after and add a deep-tree variant; run the plan property tests with `PROPTEST_CASES=500000` (AGENTS.md) to confirm identical decisions.

## 7. Compact the SFTP session's per-request bookkeeping

- **Category:** data structures
- **Evidence:** `crates/foldover-net/src/sftp.rs:100-108` stores `inflight: HashSet<u32>` and `stashed: VecDeque<(u32, Vec<u8>)>`; `id()` (`:683-686`) returns sequential wrapping IDs; `send_for` (`:696-701`) inserts into the `HashSet` per request; `receive_for` (`:740-767`) linearly scans `stashed` for the requested ID and scans it again to detect duplicates; `drain` (`:782-801`) iterates both. The window is capped at `MAX_STASHED = WINDOW = 16` (`:46`). Every observe and copy request pays these operations.
- **Hypothesis:** request IDs are sequential and the window is bounded, so a compact ring buffer indexed by `id % WINDOW` plus a pending bitmap can answer the same questions in O(1) with no hashing and no linear scans. For a workload with millions of small files and one to two requests each, that is millions of hash operations and scans removed from the SFTP hot path.
- **Proposed change:** replace `inflight` with a bitmap or a small array of outstanding IDs, and `stashed` with a fixed-size ring buffer of `[Option<Vec<u8>>; WINDOW]` indexed by `id % WINDOW`, using the pending bitmap to distinguish empty slots. Keep the existing desync detection (`duplicate`, `!inflight.contains`, stash-full) and the drain discipline exactly. The sibling [sftp-million-file-local-scan-and-wire-gaps.md](sftp-million-file-local-scan-and-wire-gaps.md) proposal 9 suggests a `HashMap` if the window grows; the ring buffer is the right structure while the window stays small.
- **Expected impact:** reduces per-request CPU and allocator work across all SFTP traffic; low-medium (the window is small, so the constant factor is modest, but it applies to every request). Confidence: **medium** on the mechanism, **low-medium** on the magnitude.
- **Effort and risk:** small-medium; the session's wire tests cover ordering and desync. Risk: an off-by-one in the ring buffer could misroute replies; add a wraparound test (IDs wrap at `u32::MAX`, which is unreachable in practice but the code uses `wrapping_add`).
- **Measurement plan:** add a micro-bench of `Session::request` against the spawned `sftp-server`; compare requests/second and allocations per 100,000 requests before/after. Run `cargo test --locked -p foldover-net sftp::`.

## 8. Add a release profile with thin LTO and one codegen unit

- **Category:** build and startup configuration
- **Evidence:** the workspace `Cargo.toml` defines no `[profile.release]` section, so release builds use Cargo defaults (`opt-level = 3`, `codegen-units = 16`, no LTO); `scripts/build.sh:150-152` builds with `--release`. Hot CPU code includes BLAKE3 streaming (`crates/foldover-fs/src/root/content.rs:12,103`), planning (`crates/foldover-engine/src/plan.rs`) and the SFTP wire codec (`crates/foldover-net/src/sftp/wire.rs`).
- **Hypothesis:** thin LTO plus `codegen-units = 1` improves the hash, plan and wire hot loops by a few percent; on a run that processes millions of entries for hours, that compounds. Every sibling document makes the same proposal; it is recorded here for completeness and cross-reference.
- **Proposed change:** add to the workspace `Cargo.toml`:
  ```toml
  [profile.release]
  lto = "thin"
  codegen-units = 1
  ```
  Keep the dev profile unchanged.
- **Expected impact:** about 5-15% off the CPU-bound portions (hashing, planning, wire codec), a few percent of end-to-end time for large trees. Confidence: **medium**.
- **Effort and risk:** trivial; longer release link times and slightly larger binaries; no behaviour change.
- **Measurement plan:** run `cargo xtask bench-check` on an idle host before/after and compare the `hash_64_mib`, `plan_100k_entries` and `scan_10k_files` medians; record the build-time delta.

## Requires approval (changes a correctness or durability contract)

These ideas are not ranked because they weaken a documented guarantee. They are listed so the trade-off is explicit.

- **Lower SQLite `synchronous` from `FULL` to `NORMAL`** (`crates/foldover-db/src/database.rs:647`; ADR 0009 requires WAL + FULL). This would cut each batch commit's fsync, but WAL `NORMAL` can lose committed batches on power loss. Proposal 1 removes a much larger commit cost without touching durability.
- **`panic = "abort"` in the release profile.** The copy workers and SFTP readers rely on `catch_unwind` to propagate panics (`crates/foldover-engine/src/run/copies.rs:198-210`, `crates/foldover-endpoint/src/sftp/readers.rs`); abort would change crash semantics.
- **Trust SFTP stat without a bounded re-read spread.** The strongest form of the sibling documents' stat-trust proposal reverses the documented stance that SFTP stat cannot prove a file unchanged (`crates/foldover-endpoint/src/sftp/readers.rs:1-6`, `sftp.rs:468-472`). Proposal 2 above does not depend on it: its local-side and snapshot-rewrite benefits stand alone, and its SFTP re-read benefit only appears if stat-trust is approved.
- **Resume interrupted SFTP copies** (`crates/foldover-endpoint/src/sftp/transfer.rs:336-357` returns 0 for SFTP targets). This reverses the documented out-of-order write decision (ADR 0034) and needs sign-off.

## Open questions and unverified items

- **Only the SQLite journal measurement was taken live.** All other magnitudes are hypotheses from reading the source; the sibling documents contain the SFTP and local-scan measurements referenced above. The one-million-row journal figure is an extrapolation from the measured quadratic coefficient, not a direct measurement.
- **The real run's batch shape may change proposal 1's constant.** The measurement used a standalone SQLite table and Python; the production path adds WAL, `synchronous=FULL`, the engine lock and rusqlite binding. The query plan is identical, so the quadratic shape holds, but the constant needs the proposed `db_commit_batches_100k` bench.
- **The post-write snapshot (proposal 2) needs the write path to supply post-write stat keys without extra round trips.** The SFTP `staged_version_on` lstat is a candidate, but the local write path's post-write metadata flow was not traced end to end here; a fallback that keeps the pre-run snapshot is required if an endpoint cannot supply a key.
- **The snapshot temp-table change (proposal 3) must preserve the exact merge semantics**, including unchanged rows left alone and the revision check; the existing `db_snapshot_*` benches are the acceptance gate.
- **The base-load overlap (proposal 5) must not build a plan against a base that changed after the scan.** The revision check at commit time catches it, but the failure mode (plan built from a stale base) needs a test.
- **The workload shape is unknown.** The fraction of runs that are first syncs versus steady-state, the direction (local→SFTP or SFTP→local), and the number of changed files determine whether proposals 1, 2 or 3 dominate. A `find | wc -l` and a change-rate sample on the target tree would settle it.
- **The untracked files in the working tree** (`crates/foldover-endpoint/tests/`, `crates/foldover-net/tests/`, `docs/performance/per-file-cost-budget.md`) were not created by this pass and were left untouched.
- **Concurrent work.** Other agents committed performance documents to this branch while this one was being written; the sibling list in the summary reflects the tree at the time of writing and may have grown. No existing file was modified by this pass.
