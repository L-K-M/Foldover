# Millions of documents over LAN SFTP: ranked pipeline proposals

Foldover is a macOS app over a portable Rust workspace (`crates/`) that previews and syncs folder pairs between local disks, NAS shares, SFTP servers and other Macs. A run opens both roots, observes each side (for SFTP: a recursive `READDIR` inventory followed by a full content read and BLAKE3 hash of every file, `crates/foldover-endpoint/src/sftp.rs` `observe_reporting`/`observe_reads`/`version_on`/`read_range_on`), reconciles the two observations against a SQLite base (`crates/foldover-engine/src/plan.rs`), then applies staged copies, metadata updates, moves and archives on a bounded worker pool (`crates/foldover-engine/src/run.rs`, `crates/foldover-engine/src/run/copies.rs`) over a pool of `ssh -s sftp` sessions speaking SFTP v3 (`crates/foldover-net/src/sftp.rs`). The workload studied here is comparing and copying millions of documents to an SFTP server on the local network; the primary metric is end-to-end wall-clock time of a sync/backup run, which for this workload is dominated by round trips per file, serial phases and per-entry CPU rather than raw bandwidth. The proposals below are ranked by expected reduction in that metric weighted by effort and risk. Code facts and line numbers were read at commit `3fbb864`; a packet-count probe and a scratch timing harness were run on this host, and those measured facts are labelled separately from the impact hypotheses, which are not guarantees.

## Ranked proposals

1. Bound SFTP reads to the observed file size
2. Overlap the two sides' observations instead of left-then-right
3. Cut per-file round trips on the SFTP write path
4. Buffer SFTP request writes
5. Replace the linear unavailable-root scan with a prefix set
6. Replace `align_spellings`' per-entry map lookups with a sorted merge
7. Batch observe-read results and store fingerprints compactly
8. Bound the SFTP startup access probe

## Measurements performed

Host: Apple M4 Max, 14 cores, 36 GiB, macOS 27.0, Rust 1.99.0, release build. The host was shared with other agents and builds, so wall-clock numbers below are noisy and descriptive, not qualification.

**SFTP read packet counts (deterministic, measured).** A temporary Rust probe linked against `foldover-net` opened each fixture through `Session::spawn`, called `open_read` → `read_all` → `close`, and verified the returned byte count. A Python framed-packet relay forwarded traffic to the local OpenSSH `sftp-server` and counted client packet type 5 (`SSH_FXP_READ`) between each `OPEN` and `CLOSE`. This is the current client's actual packet count, not a simulation:

| File bytes | READ requests | Returned data bytes |
|---:|---:|---:|
| 0 | 16 | 0 |
| 1,024 | 32 | 1,024 |
| 32,768 | 16 | 32,768 |
| 32,769 | 32 | 32,769 |
| 524,288 | 32 | 524,288 |

The 1 KiB case sends two full windows because the first window's short `DATA` reply sets `short` and the remaining `EOF` replies in that window are skipped without setting `finished` (`crates/foldover-net/src/sftp.rs:388-409`), so a second window is sent from the same offset. The temporary probe and relay were not added to the repository; proposal 1 specifies a permanent regression test.

**Scratch end-to-end timings (noisy, descriptive only).** An untracked scratch harness (`crates/foldover-endpoint/tests/scratch_perf.rs`, not committed) measured, across three runs on the loaded host: local observe of 10,000 small files at 1.2–2.1 s cold and 91 ms warm; SFTP observe of 2,000 × 8 KiB files at 169–662 ms; local→SFTP copy of those 2,000 files at 0.74–30.8 s with four threads. The copy range in particular moved with host load, so no extrapolation from these numbers is reliable. They are consistent with the code model (per-file request chains dominate) but do not prove any proposal's wall-clock benefit.

### 1. Bound SFTP reads to the observed file size

- **Title:** Bound SFTP reads to the observed file size
- **Category:** I/O and batching
- **Evidence:** Measured packet counts above. `crates/foldover-net/src/sftp.rs:32-35` defines `CHUNK = 32 * 1024` and `WINDOW = 16`; `read_from` (`:339-412`) sends a full window of 16 `READ` requests before consuming any reply, and `read_all` (`:330-336`) delegates to it. `crates/foldover-endpoint/src/sftp.rs:750-806` (`read_range_on`) already holds `expected.size`, enforces exact length, hashes the data and performs a trailing `lstat`, but does not pass the size to the transport. `read_small_on` (`:1648-1670`) calls `read_all`, so even a 64-byte identity or ignore file costs `OPEN` + 16 `READ`s + `CLOSE`.
- **Hypothesis:** Most documents are smaller than one 32 KiB chunk, so the client sends 16–32 `READ` requests where 1–2 suffice. Every extra request and reply costs a `write`/`read` syscall, SSH encryption and decryption, server request processing, and in the 1 KiB case a second window's round trip. Removing the speculative beyond-EOF requests reduces comparison cost on every SFTP run, including no-op runs.
- **Proposed change:** Add a size-bounded transport read, e.g. `Session::read_from_bounded(handle, from, len, sink)`, that sends only `min(WINDOW, ceil(remaining / CHUNK))` requests per window (at least one), requests only the remaining length in the final chunk, stops after `len` bytes, re-issues a short reply from the first unconsumed offset, and retains an `EOF`/growth probe at the expected end. Keep the exact byte-count check, the trailing `stat` verification, cancellation checks and the drain-on-error discipline (`drain`, `crates/foldover-net/src/sftp.rs:782-801`). Route `read_range_on` through it with `expected.size - from`; route `read_small_on` through a bounded read with its 64 KiB limit. Keep the unknown-length `read_all` for callers without a reliable bound.
- **Expected impact:** Hypothesis: 16–32× fewer `READ` packets for sub-32 KiB files. Because the extra requests are pipelined, the wall-clock gain is smaller than the packet-count ratio; a 20–40% reduction of the SFTP observe phase for a small-document corpus is plausible, and a few percent of end-to-end time, but this is not measured. **Confidence: high** that the excess requests occur (measured), **medium** on the end-to-end magnitude.
- **Effort and risk:** Medium, roughly 2–4 engineering days across `foldover-net` and `foldover-endpoint` plus tests. Risks: short reads, empty files, files growing or shrinking during a read, resume offsets, reordered replies, cancellation, and leaving the wire misaligned. The existing `read_from` tests and the drain logic are the reference.
- **Measurement plan:** Add a permanent wire test `known_length_read_packet_budget` beside the scripted server in `crates/foldover-net/src/sftp/tests.rs:185-265`, covering sizes 0, 1 KiB, 32 KiB, 32 KiB+1 and 512 KiB plus short, reordered, growing, truncated and cancelled reads; assert exact returned bytes and a bounded `READ` count. Run `cargo test --locked -p foldover-net sftp::` and `cargo test --locked -p foldover-endpoint sftp::`. End-to-end: time `observe_from` over a 100k × 8 KiB fixture tree and a full `foldover-cli` sync twice, comparing the second run's observe phase and total wall clock on an idle host.

### 2. Overlap the two sides' observations instead of left-then-right

- **Title:** Overlap the two sides' observations instead of left-then-right
- **Category:** concurrency and parallelism
- **Evidence:** `crates/foldover-engine/src/run.rs:773-774` runs `let mut left = observe(Side::Left, control)?;` to completion before `let mut right = observe(Side::Right, control)?;`. `EndpointPair::open` (`crates/foldover-endpoint/src/pair.rs:44-57`) also opens the two endpoints sequentially. The two endpoints are independent objects; `observe_from` takes `&self` (`crates/foldover-endpoint/src/endpoint.rs:211-229`). The run's progress sink is already atomic (`crates/foldover-service/src/sync.rs:143-171`), and the copy workers already share a stop flag with the run thread (`crates/foldover-engine/src/run/copies.rs:198-225`).
- **Hypothesis:** For a local↔SFTP pair the local scan is CPU/disk-bound while the SFTP scan is network-bound, so they do not contend for the same resource. Overlapping them removes `min(T_left, T_right)` from the critical path — potentially the entire local scan. The scratch harness measured local observe at 120–210 µs/file and SFTP observe at 85–331 µs/file on a loaded host, so for a million-file local side the local scan is a large serial term.
- **Proposed change:** Run the two `observe_from` calls on two scoped threads sharing an atomic stop flag and a shared progress sink; join both before `align_spellings` (`run.rs:777-778`). Keep error ordering deterministic (report the left failure first, as today). Refactor the `observe` closure so `control` is a shared `Control` (an `AtomicBool` plus the underlying callable behind a `Mutex`) rather than `&mut`, mirroring the `Copies` worker pattern. Confirm `RunProgress: Sync` (its production implementation only touches atomics and a `Mutex<Instant>`) or wrap the sink in a `Mutex`.
- **Expected impact:** Hypothesis: removes the smaller side's scan time from every run — an estimated 20–40% of the compare phase for a local↔SFTP million-file pair, and near-zero when one side is tiny or both sides are equally slow. **Confidence: high** on the mechanism, **medium** on the magnitude (the local scan's share depends on the tree and changed fraction).
- **Effort and risk:** Medium, roughly 2–4 days. Risks: cancellation must stop both scans; progress callbacks must be thread-safe; error ordering must not change; `Endpoint`/`Observation` must be `Send + Sync`. No protocol or correctness change.
- **Measurement plan:** Time `PairRun::prepare` on a pair with a 100k-file local tree and a fixture SFTP tree before/after; assert that `ObserveStep` counts from the two sides interleave in a tracing shim. Run `cargo test --locked -p foldover-engine run::tests` and `cargo test --locked -p foldover-endpoint sftp::`.

### 3. Cut per-file round trips on the SFTP write path

- **Title:** Cut per-file round trips on the SFTP write path
- **Category:** redundant work and caching
- **Evidence:** `crates/foldover-endpoint/src/sftp/transfer.rs:446-531` (`send_on`) issues, strictly serialized within one file: `receiving_on` → `attributes_on` → `lookup_on` → `lstat` (`:419-444`, `spelling.rs:94-118`); `upload_on` → `write_new` → `create_new` + pipelined `WRITE`s + `CLOSE` (`sftp.rs:888-919`, `:1672-1688`); `set_metadata_on` → its own `lstat` and maybe `SETSTAT` (`sftp.rs:940-980`); `staged_version_on` → a second `lstat` of the same staged file (`sftp.rs:921-934`); then `place_on` → `lookup_on` + `listed_on` + `set_aside_on` + rename (`sftp.rs:1034-1082`). `set_aside_on` (`sftp.rs:1083-1102`) calls `make_directories_on` for every archived file's parent, and `make_directories_on` (`sftp.rs:1606-1641`) attempts `MKDIR` for every component and, on the usual already-exists refusal, performs an `LSTAT`, without consulting the `listings` cache that already records folders seen or created this run (`sftp.rs:103-105`, `spelling.rs:201-233`).
- **Hypothesis:** For millions of small documents the apply phase is dominated by fixed per-file request chains, not bytes. The two post-write `LSTAT`s of the same staged file can be one, and archive parent folders confirmed earlier in the run need not be re-walked over the network. Removing 1–3 round trips per file is a direct apply-phase win.
- **Proposed change:** In `send_on`'s file branch, have `set_metadata_on` return the attributes it fetched (re-stat only when it actually sent `SETSTAT`) and pass them to `staged_version_on`, preserving the rule that the recorded version describes the target's final stored state. In `make_directories_on`, consult the `listings` cache: skip components present as `FolderView::Cached` or created this run via `note_added`; on a `Dirty` entry or a cache miss, fall back to the existing `MKDIR`/`LSTAT` walk and invalidate on failure. Keep the post-place `attributes_on` check and the destination-version checks unchanged.
- **Expected impact:** Hypothesis: 15–30% off apply-phase wall time for create- and replace-heavy small-file runs; negligible for large files and first copies into empty folders. **Confidence: medium-high** on the request-count reduction (verified in code), **medium** on the wall-clock magnitude.
- **Effort and risk:** Small-medium, contained in `send_on`/`place_on`/`set_metadata_on`/`staged_version_on`/`make_directories_on`. Risks: recording a version from stale attributes; a cache that lies about a parent after an external client removes it; Unicode spelling. The existing `Dirty` discipline and post-place checks bound these; a missing parent must fall back to the network walk once.
- **Measurement plan:** Shim `Session::request` (`crates/foldover-net/src/sftp.rs:689-694`) to count request types during a 10k-file create run and a 10k-file replace run against the fixture `sftp-server`; compare requests per file and wall clock. Run `cargo test --locked -p foldover-endpoint sftp::` and `cargo test --locked -p foldover-engine run::tests`.

### 4. Buffer SFTP request writes

- **Title:** Buffer SFTP request writes
- **Category:** I/O and batching
- **Evidence:** `crates/foldover-net/src/sftp.rs:97-98` stores `input: File` (unbuffered) beside `output: BufReader<File>` (buffered). `send_until` (`:714-738`) writes each packet directly with `File::write`. `read_from` (`:348-366`) calls `send_for` 16 times per window; `queue_write` (`:471-500`) calls it once per 32 KiB chunk; `request` (`:689-693`) sends one packet and then waits for its reply. A 1 KiB file therefore causes 32 request `write` syscalls, and a million such files cause tens of millions.
- **Hypothesis:** The write side is unintentionally unbuffered while the read side is buffered. Batching request packets and flushing before waiting for replies reduces syscalls, context switches and pipe overhead on both the client and the `ssh` subprocess. The effect is largest for small-file workloads with many tiny request packets.
- **Proposed change:** Wrap `input` in a `BufWriter<File>` (or a reusable batch `Vec<u8>`) and flush at every point where the client starts waiting for a reply: in `request` before `receive_for`, in `read_from` after sending a window, and in `queue_write` before collecting the oldest reply. Keep `nonblocking` on the underlying file, the `io_timeout` accounting, and the `inflight` bookkeeping. Ensure a failure to flush marks the session failed exactly as a failed write does today.
- **Expected impact:** Hypothesis: 5–15% lower client CPU on small-file workloads and fewer pipe writes per packet; little effect on large-file throughput, which is already window-limited. **Confidence: medium** (mechanism is clear; magnitude unmeasured).
- **Effort and risk:** Small-medium. The main risk is forgetting to flush before a wait, which would deadlock the session; cover with the existing wire tests for pipelined reads/writes, timeouts and drain-on-error. A `BufWriter` panics if a write fails after a partial flush, so the error path must be checked.
- **Measurement plan:** Count `write` syscalls with `dtrace`/`strace` or a thin wrapper around the session during `observe_from` and a 10k-file copy; compare request counts, wall clock and CPU. Run `cargo test --locked -p foldover-net sftp::` and `cargo test --locked -p foldover-endpoint sftp::`.

### 5. Replace the linear unavailable-root scan with a prefix set

- **Title:** Replace the linear unavailable-root scan with a prefix set
- **Category:** algorithmic complexity
- **Evidence:** `crates/foldover-endpoint/src/sftp.rs:1718-1725` defines `unavailable(observation, path)` as `observation.unavailable.iter().any(|root| root == path || root.is_ancestor_of(path))`. It is called per directory at `:556-560`, per read at `:562-568`, and in the final `observation.entries.retain` at `:576-581`. The local endpoint already solves this with `UnavailablePaths` (`crates/foldover-endpoint/src/local.rs:437-470`), a `BTreeSet` of root byte strings where `contains` tests the full path and each `/` prefix in `O(log U)`. The SFTP path is `O(N × U × path_len)`; the local path is `O(N × log U × path_len)`.
- **Hypothesis:** On a server with many unreadable directories (permission-denied folders, broken links, subtrees that vanish mid-scan), the SFTP observe path becomes quadratic in the number of unavailable roots. A prefix set removes the linear scan without changing which entries are suppressed.
- **Proposed change:** Reuse the `UnavailablePaths` pattern in the SFTP observe path: after the listing pass, build a `BTreeSet<Vec<u8>>` of unavailable root keys once, then test each path by checking the full path and each `/`-separated prefix against the set. Use it in the directory-settle loop, the `reads.retain`, and the final `entries.retain`. Preserve the existing `is_ancestor_of` semantics: a root suppresses itself and its descendants, but not a sibling whose name merely shares a prefix (`a` must not suppress `a-b`).
- **Expected impact:** Hypothesis: `O(N × U)` → `O(N log U)`; large when `U` is in the hundreds or thousands, negligible when `U` is small. Because the common case has few unavailable roots, the end-to-end effect is usually small, but it removes a pathological stall on servers with many denied folders. **Confidence: high** on the complexity, **medium** on how often the pathological case occurs.
- **Effort and risk:** Small. The local implementation is the reference; the risk is a prefix that is not a component boundary. Cover with tests where an unavailable root is a string prefix of another path but not an ancestor (`a` vs `a-b`, `a` vs `a/b`).
- **Measurement plan:** Add a test/bench with 100k entries and 1,000 unavailable roots; time `observe_from` before/after and assert the surviving entry set is identical. Run `cargo test --locked -p foldover-endpoint sftp::`.

### 6. Replace `align_spellings`' per-entry map lookups with a sorted merge

- **Title:** Replace `align_spellings`' per-entry map lookups with a sorted merge
- **Category:** algorithmic complexity
- **Evidence:** `crates/foldover-engine/src/run.rs:1511-1558` (`align_spellings`) iterates `base.keys()` and calls `observation.entries().contains_key(path)` for each (`:1526-1532`), then chains `observation.entries().keys()` with `observation.unavailable()` and filters with `base.contains_key(*path)` (`:1537-1545`). Both `base` and `observation.entries()` are `BTreeMap`s sorted by `SyncPath`. For a million entries this is roughly 20 million key comparisons per run, on the run thread, even when nothing was respelled.
- **Hypothesis:** The per-entry lookups are wasted work: both inputs are already sorted, so a single merge can compute the base keys missing from the observation and the observation keys missing from the base in `O(n)` with no per-entry tree traversal.
- **Proposed change:** Merge the two sorted iterators: walk `base.keys()` and `observation.entries().keys()` together, collecting base keys absent from the observation (keyed by composed form, with the existing ambiguity rule that two base paths composing alike map to neither) and observation keys absent from the base. Preserve the destination-uniqueness check (`:1548-1558`) and the `UnavailablePaths` chaining. Avoid cloning paths until a respelling is confirmed.
- **Expected impact:** Hypothesis: 1–3 s per million entries on the run thread, a small end-to-end effect (planning is CPU-only and usually secondary to network I/O), larger on deep or Unicode-heavy trees. **Confidence: high** on the complexity, **medium-low** on the wall-clock magnitude.
- **Effort and risk:** Small-medium. Decision-equivalence must be preserved; `align_spellings` has unit tests in `crates/foldover-engine/src/run/tests.rs` (search for respell/respelled cases). The risk is a base key absent from the observation whose composed form matches an observation key that is itself in the base under another spelling.
- **Measurement plan:** Add a 1M-entry `align_spellings` bench (or extend the existing `plan_100k_entries` bench in `crates/foldover-engine/benches/plan.rs` with a respelling variant) and compare ns/path and allocations; run `cargo test --locked -p foldover-engine` and `cargo test --locked -p foldover-endpoint sftp::`.

### 7. Batch observe-read results and store fingerprints compactly

- **Title:** Batch observe-read results and store fingerprints compactly
- **Category:** allocation and memory layout
- **Evidence:** `crates/foldover-endpoint/src/sftp/readers.rs:46-92` (`read_each`) sends one `(usize, ObservedEntry)` per file over an `mpsc` channel; `collect` (`:97-125`) receives them one at a time and inserts each into `observation.entries`, a `BTreeMap` (`crates/foldover-endpoint/src/local.rs:425-427`). `ObservedEntry` (`local.rs:381-385`) contains a `Fingerprint` whose `key` is a `Vec<u8>` allocated per entry (`local.rs:293-299,317-328`); the SFTP stat key is built with `stat_key` and is at most 128 bytes (`crates/foldover-fs/src/root.rs:296`, `crates/foldover-endpoint/src/sftp.rs:1735-1745`). For a million files that is a million channel messages, a million small `Vec` allocations and a million `BTreeMap` inserts.
- **Hypothesis:** Batching results in chunks reduces synchronization and improves cache locality; storing the fingerprint key in a small inline buffer removes a million allocations and reduces the observation's memory footprint. Neither changes the protocol or the persisted snapshot format.
- **Proposed change:** Change `readers::read_each` to send `Vec<(usize, R)>` batches: workers accumulate up to a fixed batch size (e.g. 256) before sending, and `collect` drains batches with `try_recv`/`recv_timeout` and feeds the existing `landed` closure per item. Change `Fingerprint.key` to a small inline buffer (e.g. `smallvec::SmallVec<[u8; 64]>` or a fixed `[u8; 128]` with a length), keeping `to_bytes`/`from_bytes` (`local.rs:355-378`) byte-for-byte compatible so existing snapshots remain readable. If a new dependency is undesirable, a `Box<[u8]>` with a bump/arena allocator for the observe phase is an alternative.
- **Expected impact:** Hypothesis: single-digit to ~15% of observe/plan CPU and a lower peak memory mark on million-entry trees; no change to correctness or the wire. **Confidence: medium-low** until an allocation/RSS profile is taken.
- **Effort and risk:** Medium. The channel batching is easy and self-contained; changing `Fingerprint` touches local and SFTP observations, snapshot encoding/decoding and their tests. Risks: breaking `to_bytes`/`from_bytes` compatibility (keep the format identical), and a larger inline `Fingerprint` increasing the size of every `ObservedEntry` even when the key is short.
- **Measurement plan:** Add an allocation counter (a `#[global_allocator]` wrapper in a bench) and measure allocations/entry and peak RSS for a 1M-entry observe; compare observe-phase wall clock before/after. Run `cargo test --locked -p foldover-endpoint sftp::`, `cargo test --locked -p foldover-endpoint local::`, and `cargo test --locked -p foldover-engine`.

### 8. Bound the SFTP startup access probe

- **Title:** Bound the SFTP startup access probe
- **Category:** build and startup configuration
- **Evidence:** `crates/foldover-endpoint/src/endpoint.rs:155-157` calls `endpoint.probe_access()` immediately after opening an SFTP root. `crates/foldover-endpoint/src/sftp.rs:261-266` implements that probe with a complete `read_dir(&self.root)` whose returned entries are discarded. `observe_reporting` (`sftp.rs:482-503`) later lists the root again. For a flat root with a million entries, the probe enumerates and materializes the whole root listing just to establish that listing is permitted.
- **Hypothesis:** A bounded permission probe — open the directory, request one `READDIR` batch, treat `EOF` as success for an empty directory, then close — detects the permission failures the probe exists to catch without materializing the root. The full scan cost remains, but the startup spike and duplicate enumeration disappear.
- **Proposed change:** Add a transport-level bounded list-access operation (e.g. `Session::list_access`), or a `read_dir_bounded(limit)` that opens the directory, sends one `READDIR`, consumes the reply (or `EOF`), and closes. Use it in `SftpEndpoint::probe_access`. Preserve the distinction between "opening is allowed but listing is refused" and "the directory is empty"; propagate real failures and timeouts; do not cache the probe's listing for observation.
- **Expected impact:** Hypothesis: 1–5% of total time on very wide-root, tiny-file runs, with a much larger reduction in endpoint-opening latency and peak memory for such roots; negligible on small roots. **Confidence: low-medium** until root width and the observe phase are timed separately.
- **Effort and risk:** Small, roughly 1–2 days in the net/endpoint boundary. Risks: a server that allows `OPENDIR` but refuses `READDIR` (the probe must surface that), a server that returns `EOF` immediately for an empty directory (must count as success), and a `CLOSE` failure after a successful probe (must not be swallowed).
- **Measurement plan:** Add a scripted-server test `list_access_probe_is_bounded`; assert a bounded `READDIR` count, success on an empty directory, and a visible permission error. Compare endpoint-open time, `READDIR` response bytes, peak RSS and full-run wall clock on roots of 1k/100k/1M entries. Run `cargo test --locked -p foldover-net sftp::` and `cargo test --locked -p foldover-endpoint sftp::`.

## Rejected or requires approval

These ideas change a documented correctness or durability contract, so they are not ordinary optimizations and should not be implemented without an ADR update and owner approval.

- **Skip the SFTP content re-read when the stat fingerprint is unchanged.** `crates/foldover-endpoint/src/sftp/readers.rs:1-6` and the comment at `sftp.rs:644-646` state the intentional stance that SFTP stat cannot prove a file unchanged, and `crates/foldover-endpoint/src/sftp/tests.rs` deliberately tests content changes hidden behind unchanged attributes. Reusing the local endpoint's racy-window heuristic for SFTP would reverse that stance. The local endpoint already avoids the re-read (`local.rs:1198-1204`), so this is a real win on steady-state runs, but it is a safety-policy change, not a transparent optimization.
- **Change SQLite `synchronous` from `FULL` to `NORMAL`.** `crates/foldover-db/src/database.rs:647` sets `FULL`, and ADR 0009 requires "WAL, FULL synchronous mode". In WAL mode `NORMAL` is safe against process crashes but not against power loss; the apply phase commits once per 256 rows, so this is a meaningful performance lever, but it weakens the documented durability contract.
- **Batch per-file `fsync`s for local destinations.** `crates/foldover-fs/src/root/write.rs:869-876` flushes every file and directory at `Durability::Standard` (e.g. `:210`, `:237`, `:310`), and ADR 0019 defines that contract. Batching directory syncs would help SFTP→local restores and local backups, but it changes crash semantics and is outside the stated SFTP-destination workload.
- **Raise `COMMIT_BATCH` or make root-identity checks time-based.** ADR 0020 specifies base commits "in batches of 256". `crates/foldover-engine/src/run.rs:52` and `:1233-1245` implement that, and `check_roots` (`:1378-1397`) re-reads both identities every 256 rows. Larger batches or a time-based check would cut a real per-batch cost on million-change runs, but they increase crash-recovery redo volume and change a documented design decision.
- **Raise `PARALLEL_COPIES` from 4 to 8.** ADR 0043 sets `PARALLEL_COPIES = 4` (`crates/foldover-endpoint/src/sftp.rs:68-70`) with a table of per-device limits, while PLAN.md §4.9 allows "network 4–8 connections". The session pool already clamps on refusal (`sessions.rs`), so this is a low-risk change, but it contradicts an implemented ADR and needs that ADR updated first.

## Open questions and unverified items

- No live profile, million-file run, real LAN/NAS run or allocation trace was collected. All wall-clock magnitudes above are hypotheses; only the SFTP `READ` packet counts were measured directly, and the scratch timings are too noisy to extrapolate.
- The actual document-size distribution, directory depth, changed fraction, sync mode, archive volume and server `MaxSessions` are unknown. These determine the ranks: proposal 1 is largest for sub-32 KiB files, proposal 2 for local↔SFTP pairs with a large local tree, proposal 3 for replace-heavy runs, proposal 5 for trees with many unreadable folders, and proposal 8 for very wide roots.
- The scratch harness and packet probe were temporary and are not committed; the measurement plans above specify permanent regression tests. The untracked `crates/foldover-endpoint/tests/scratch_perf.rs` was used as a scratch harness (its warm-cache assertion was temporarily adjusted and then restored byte-for-byte to the original content).
- The `read_from` bounded-read change must preserve the existing behavior for files that change during a read, including the `ScanError::Changed` path and the trailing `stat` comparison.
