# Performance proposals: local scan syscalls, name handling, and wire buffers for million-file SFTP runs

Foldover is a macOS app over a portable Rust engine (`crates/`) that syncs folder pairs between local disks, shares, SFTP servers and other Macs. A run observes both endpoints, plans against a SQLite-backed base, then applies copies, metadata updates, moves and archives over pooled `ssh -s sftp` sessions. The workload studied here is comparing and copying millions of documents to an SFTP server on the local network; the primary metric is end-to-end wall-clock time of a sync/backup run. Four sibling passes already cover the SFTP-side scan re-read, apply-time verification re-read, directory-listing pipelining and parallel listing, copy-window sizing, write-path round trips, commit/identity batching, journal and resolution-table deletes, archive parallelization, snapshot skipping, planner ancestor walks and `skip_branches`, Unicode key fast paths, allocation churn, and the release profile ([lan-sftp-end-to-end-sync.md](lan-sftp-end-to-end-sync.md), [sftp-million-file-hot-paths.md](sftp-million-file-hot-paths.md), [sftp-million-file-run-costs.md](sftp-million-file-run-costs.md), [sftp-million-file-db-apply-hot-paths.md](sftp-million-file-db-apply-hot-paths.md)). This document is a complementary pass over costs those passes do not name: the local side's per-file syscall chain and policy-blind extended-metadata capture, the repeated Unicode name-key normalization across every planner pass, respelled-name lookup probes on the SFTP apply path, the exact small-file read amplification in `foldover-net`, the base's `BTreeMap` representation, peak memory across the whole-tree buffers, and the extra copy in `write_chunks`. Everything below was read in source at the current checkout; nothing was executed or profiled in this session, so every impact magnitude is a hypothesis with an explicit confidence level, not a measured fact. The existing criterion benches and budgets in [perf/README.md](../../perf/README.md) are the natural harness for the CPU-side items.

## Ranked proposals

1. Make the local extended-metadata capture policy-aware
2. Compute each path's normalized name key once per run
3. Size SFTP reads to the known file length and drop the second window
4. Fuse the local extended-metadata read and content hash into one open
5. Resolve respelled SFTP names from the cached folder listing
6. Allow parallel copies for one-way SFTP↔SFTP pairs
7. Store the base as a sorted `Vec` and binary-search it
8. Cut peak memory with an arena/streaming tree representation
9. Remove the extra copy in `write_chunks` and size the read buffer to the packet

### 1. Make the local extended-metadata capture policy-aware

- **Category:** redundant work and caching
- **Evidence:** `crates/foldover-endpoint/src/local.rs:1233-1255` — `entry_version` calls `optional_extended_metadata` (local.rs:1258-1272) for every file that is not proven unchanged, then calls `hash_file`. `crates/foldover-fs/src/root/extended.rs:273-303` — `capture` always reads every extended attribute's value and digest (`:281-293`), always reads the ACL (`access_control(file)?` at `:296`), and re-lists the attribute names at the end (`:297`). `crates/foldover-fs/src/mac_metadata.rs:82-122` — the ACL read is `acl_get_fd_np` + `acl_size` + `acl_copy_ext`. But `crates/foldover-endpoint/src/local/version.rs:103-139` — `metadata_digest` hashes the ACL only under `(Propagation::Sync, _)` (`:109-114`); under the default `Propagation::Ignore` policy (`crates/foldover-types/src/metadata_policy.rs:67-71`) it hashes only the executable bit (`:115-118`), and for a symlink it hashes no permissions at all (`:107-108`). Under `extended_attributes: Ignore` it returns at `:136-139` without hashing any non-fork attribute. `attribute_names` itself costs two `flistxattr` calls (`extended.rs:306-317`), and `capture` calls it twice (`:277`, `:297`).
- **Hypothesis:** on the default policy, every scanned file pays for an ACL retrieval that the version never uses, plus a second `flistxattr` sweep that can find nothing to change when the first list was empty. Under `extended_attributes: Ignore`, every non-fork xattr is still read and digested even though the version ignores it. For a first sync or high-churn run over millions of files, these are pure syscalls and copies on the local scan thread.
- **Proposed change:** thread the `MetadataPolicy` into `Root::read_extended_metadata`/`capture` (the write path keeps a "capture everything" mode). When `policy.permissions() == Ignore`, skip `access_control`. When the initial attribute-name list is empty, skip the trailing `attribute_names` change check. When `policy.extended_attributes() == Ignore`, read only the resource-fork attribute's value/digest (the fork is content and always hashed, version.rs:47-58) and skip the rest. Keep the `EntryMetadata` before/after checks unchanged.
- **Expected impact:** removes 1-3 syscalls per file on the default policy and most of the per-xattr work under `Ignore`; estimated 5-15% off the local scan phase for million-file first syncs, near-zero on incremental scans where stat reuse dominates. Confidence: **high** that the ACL and duplicate `flistxattr` are wasted under the default policy (code is explicit), **medium** on the wall-clock magnitude.
- **Effort and risk:** small-medium; the policy must be passed only into the observe path, never into `native_metadata` (`crates/foldover-endpoint/src/local/foreign.rs:51-68`), which needs every attribute to write. Regression risk: a version computed from a filtered capture must be identical to today's; the existing `version.rs` tests and `crates/foldover-fs/src/root/extended/tests.rs` cover the digest inputs.
- **Measurement plan:** extend `scan_10k_files` (or add `local_scan_10k_files`) with a variant that counts syscalls via `strace -c -f` or `dtruss` on macOS, and a variant that times `observe_from` over 10k files with the default policy before/after. Add a unit test asserting `entry_version` is unchanged for a file with xattrs and an ACL under both policies.

### 2. Compute each path's normalized name key once per run

- **Category:** algorithmic complexity / redundant work
- **Evidence:** `crates/foldover-engine/src/plan.rs:421-439` — `name_key` does `text.nfc().collect::<String>()` and, for case-insensitive matching, `text.to_lowercase()`, allocating per call. It is called for every row in `mark_name_clashes` (`plan.rs:365`, `:379`), in `protect_unavailable` (`plan.rs:125`, `:142`, `:149`), in `protect_uncertain_absences` (`plan.rs:189`, `:191`), in `unavailable` (`crates/foldover-engine/src/run.rs:1955`, `:1961`), and in `uncertain_absences` (`run.rs:1995`, `:2004`, `:2020`). `align_spellings` (`run.rs:1519-1522`) composes every base path and every observed path with another `nfc().collect()`. The ignored budget test `unicode_respelling_prepare_budget` (`crates/foldover-engine/src/run/tests.rs:806-839`) allows 50k respelled names in 5 s, i.e. 100 µs/name of headroom.
- **Hypothesis:** for a 1M-entry tree, the planner performs roughly six full O(n) normalization passes (clashes, two protect passes, unavailable, uncertain absences, spelling alignment), each allocating a `String`/`Vec<u8>` per path. The same path is normalized repeatedly in the same run. This is CPU and allocator work on the run thread while the network is idle.
- **Proposed change:** compute a normalized key once per distinct path per run and reuse it. Concretely: give `PlanRow` (or a parallel `Vec`) a `Cow<[u8]>` name key computed at row creation; have `protect_unavailable`/`protect_uncertain_absences`/`mark_name_clashes` read it instead of calling `name_key`; and memoize `align_spellings`'s composed keys in a `HashMap<&[u8], Vec<u8>>` or compute them while building the observation. The ASCII fast path in [sftp-million-file-db-apply-hot-paths.md](sftp-million-file-db-apply-hot-paths.md) proposal 7 is complementary and should land first.
- **Expected impact:** removes millions of NFC collections and allocations per run; estimated 2-8% off plan/prepare CPU for million-entry trees, and a larger fraction of `align_spellings` on respelled trees. Confidence: **high** that the repeated passes exist, **medium** on the magnitude (depends on path length and non-ASCII fraction).
- **Effort and risk:** medium; the key type change touches every `name_key` caller and the `BTreeSet`/`HashMap` key types. Risk: a caller that stores a key after the path is mutated; keys must be computed from immutable paths. The plan's unit tests and `plan_properties` proptests cover decision equivalence.
- **Measurement plan:** run `cargo xtask bench-check` (`plan_100k_entries`) before/after; add a 1M-entry plan variant and an allocation counter in a bench to count keys per row. Re-run the ignored `unicode_respelling_prepare_budget` test with `--ignored --nocapture` and compare its printed elapsed time.

### 3. Size SFTP reads to the known file length and drop the second window

- **Category:** I/O and batching
- **Evidence:** `crates/foldover-net/src/sftp.rs:339-415` — `read_from` sends a full `WINDOW` = 16 `READ` requests (`:350-366`) before consuming any reply, and after a short read it sets `short` and discards the remaining replies (`:388-409`), then starts another full window. For a file smaller than one `CHUNK` (32 KiB, `sftp.rs:32`), the first window sends 16 requests, the first reply carries the data, the next 15 are EOF, and the second window sends 16 more to discover EOF: 32 `READ` requests and 32 replies for one chunk of data. For a file whose size is not a multiple of 32 KiB, the final window is likewise mostly wasted. `read_all` (`sftp.rs:330-337`) inherits this, so `read_small_on` (`crates/foldover-endpoint/src/sftp.rs:1648-1670`) pays 32 requests for the 64-byte identity file. `check_roots` (`crates/foldover-engine/src/run.rs:1378-1397`) calls `identity()` every `COMMIT_BATCH` = 256 rows (`run.rs:52`, `:1233-1245`), so a 1M-row run issues ~3900 identity reads per side. The sibling passes propose the same window cap ([sftp-million-file-hot-paths.md](sftp-million-file-hot-paths.md) proposal 5, [sftp-million-file-run-costs.md](sftp-million-file-run-costs.md) proposal 3); this entry records the exact request count and the control-plane amplification.
- **Hypothesis:** the request amplification is worst exactly where the workload is heaviest: small documents and tiny control-plane files. Cutting the window to the known length removes up to 31 of 32 requests per small file and the wasted tail window for every larger file, reducing client and server CPU as well as the final drain round trip.
- **Proposed change:** add a size-aware read (e.g. `read_known(handle, from, len, sink)`) that sends `min(WINDOW, ceil(remaining / CHUNK))` requests per round, with the last request asking for exactly the remaining bytes, and stops after the first short read or EOF. Route `read_range_on` (which has `expected.size`, sftp.rs:750-805) and `read_small_on` (which can `lstat` first or read a single chunk and stop on short/EOF) through it. Keep the existing overrun/short-read validation.
- **Expected impact:** 32x fewer `READ` requests for files under 32 KiB and up to 2x fewer for large non-multiple files; estimated 10-30% off the SFTP observe phase for small-document corpora and a large reduction in identity-check traffic. Confidence: **high** on the request counts (verified in code), **medium** on the wall-clock magnitude (the wasted requests are pipelined, so the win is mostly CPU and the final drain RTT).
- **Effort and risk:** small-medium; one new read loop in `foldover-net` plus call-site swaps. Risk: EOF/short-read edge cases and servers that answer less than requested; the existing tests in `crates/foldover-net/src/sftp/tests.rs` and the overrun check at sftp.rs:783-787 cover them.
- **Measurement plan:** add a packet-counting shim around `Session::send_for` (`sftp.rs:696-701`) and count `READ` requests during `observe_from` over a 10k-small-file fixture tree and during a 100k-row `check_roots` loop; compare before/after. Add a criterion bench `sftp_read_1k` against the spawned `sftp-server`.

### 4. Fuse the local extended-metadata read and content hash into one open

- **Category:** I/O and batching
- **Evidence:** `crates/foldover-endpoint/src/local.rs:1233-1255` — `entry_version` calls `optional_extended_metadata` and then `hash_file`, two independent operations on the same path. `crates/foldover-fs/src/root/extended.rs:170-208` — `read_extended_metadata` does `EntryMetadata::at` (fstatat), `openat`, `EntryMetadata::from_file` (fstat), `capture`, then `EntryMetadata::from_file` and `self.metadata(path)` again. `crates/foldover-fs/src/root/content.rs:44-92` — `open_observed_file` does `EntryMetadata::at` (fstatat), `openat`, `EntryMetadata::from_file` (fstat); `stream_observed_file` (`:94-129`) then reads and finishes with `EntryMetadata::from_file` and `self.metadata(path)`. So one scanned file costs two opens and roughly eight stats before any data is hashed.
- **Hypothesis:** the extended-metadata read and the content hash both open the same observed file and both verify its identity. Fusing them into one open (read xattrs/ACL from the same descriptor used for the data, then do the post-read checks once) removes one open and roughly four stats per file. For a first sync of millions of small files this is a direct cut in local-scan syscalls.
- **Proposed change:** add a combined `Root::read_extended_and_hash` (or a `hash_file` variant that takes an already-open descriptor plus a closure for the extended capture) that opens the observed file once, captures extended metadata from that descriptor, streams the data through BLAKE3, and performs the final identity checks once. Keep the existing `open_observed_file` checks and the `prevent_materialization` discipline; the write path is unchanged.
- **Expected impact:** one fewer open and roughly four fewer stats per scanned file; estimated 5-15% off the local scan phase for first syncs and high-churn runs, near-zero on incremental scans. Confidence: **medium** (the call chains are verified; the syscall count is inferred from the code and should be confirmed with a tracer).
- **Effort and risk:** medium-high; the combined path must preserve the exact ordering of the metadata checks and the cancellation checkpoints, and the extended capture must see the same descriptor state as the hash. Risk: a subtle change in the `Changed` detection order could mask a concurrent edit; the existing `content.rs` and `extended/tests.rs` cases are the safety net.
- **Measurement plan:** use `dtruss`/`strace -c -f` on a 10k-file `observe_from` before/after and compare `open`/`fstatat` counts; add a criterion bench `local_hash_10k_files` that times `entry_version` over previously unseen files. Run the existing `crates/foldover-endpoint/src/local.rs` and `crates/foldover-fs` tests.

### 5. Resolve respelled SFTP names from the cached folder listing

- **Category:** redundant work and caching
- **Evidence:** `crates/foldover-endpoint/src/sftp/spelling.rs:48-84` — `on_stored_with` runs the operation on the given path and, on `NotFound` for a respellable path, calls `respelled_on`. `respelled_on` (`:468-485`) walks every path component and, for each, tries each spelling with an `lstat` (`:481-484`), so a miss on a path with N components costs up to 2N `LSTAT` round trips. `lookup_on` (`:94-118`) is the main caller and is used by `receiving_on` for `Expected::Absent` (`crates/foldover-endpoint/src/sftp/transfer.rs:419-444`), i.e. before every new file is created. The endpoint already keeps a per-folder listing cache (`crates/foldover-endpoint/src/sftp.rs:103-105`; `listing_on` at `spelling.rs:145-198`, bounded by `LISTED_FOLDERS` = 512 at `:28`), and `note_added` updates a cached folder in place (`:201-219`). The scan itself lists directories directly (`sftp.rs:503`) and does not populate this cache.
- **Hypothesis:** for a corpus with non-ASCII names, every new file whose path is stored in another normalization pays up to 2N `LSTAT`s to discover that no composing match exists. A folder listing already answers that question in one `READDIR`; the cache makes repeated lookups in the same folder free.
- **Proposed change:** in `respelled_on`, resolve each component from the parent's listing: if the parent is in the `listings` cache as `Cached`, search its names for a composing match (the same operation `listed_on` already does at `:120-143`); if it is absent or `Dirty`, fall back to the current per-component `lstat` probes (or fetch the listing once if the path is deep). Populate the cache from the scan's `read_dir` results where the bound allows, and consider raising `LISTED_FOLDERS` or making the bound byte-based rather than folder-count-based. Keep the `Dirty` discipline so a concurrent external change forces a refetch.
- **Expected impact:** turns up to 2N `LSTAT`s per missing respellable name into zero or one `READDIR`; for a non-ASCII-heavy corpus with deep paths this is a large apply-phase reduction, for an ASCII corpus it is inert (`respellable` returns false for ASCII, `spelling.rs:493-501`). Confidence: **high** on the probe cost (code is explicit), **medium** on the magnitude (depends on the non-ASCII fraction and cache hit rate).
- **Effort and risk:** medium; the cache bound and invalidation must be respected, and a wrong answer could write a path in the wrong spelling. Risk is bounded by the existing `Dirty` marking and the post-place `attributes_on` check (`sftp.rs:1069`). Existing `crates/foldover-endpoint/src/sftp/tests.rs` cases cover respelled writes.
- **Measurement plan:** count `LSTAT` requests per created file for a fixture tree with decomposed and composed names (shim around `Session::request`), before/after; compare end-to-end apply time for 10k non-ASCII creates. Confirm the respelling tests still pass.

### 6. Allow parallel copies for one-way SFTP↔SFTP pairs

- **Category:** concurrency and parallelism
- **Evidence:** `crates/foldover-engine/src/run.rs:1430-1442` — `workers()` returns `NonZeroUsize::MIN` whenever both endpoints are SFTP, with the comment that two opposite-direction copies could each hold one server's session while waiting for the other's. The copy path acquires the destination session first (`crates/foldover-endpoint/src/sftp/transfer.rs:207`) and then, inside `send_on`, acquires the source session (`transfer.rs:505-528` → `source.push` → `read_file_from` → `read_range` → `session_unless_cancelled`, `crates/foldover-endpoint/src/sftp.rs:737-747`). `source()` itself acquires and releases a source session before the destination is taken (`transfer.rs:364-410`), so the only nested acquisition is destination→source. `SyncMode::Backup`/`Mirror` have a single source and target (`crates/foldover-types/src/pair.rs:140-153`), and `keep_both` runs outside the copy worker pool (`crates/foldover-engine/src/conflict.rs:29-38`).
- **Hypothesis:** in a one-way pair every copy goes the same direction, so the destination→source acquisition order is consistent and the deadlock the guard prevents cannot arise. Forcing one worker throws away up to 4x copy throughput on SFTP→SFTP backups; the session pool already clamps when a server refuses connections (`crates/foldover-endpoint/src/sftp/sessions.rs`).
- **Proposed change:** in `workers()`, when both endpoints are SFTP, inspect the plan's copy directions: if every `EntryDecision::Propagate { from }` has the same `from` (or there are no copies), return `min(left.workers(), right.workers())`; otherwise return 1. This also covers a person's choice that copies a change back into a Backup source, which would make the directions mixed. Keep the existing refusal clamp.
- **Expected impact:** up to ~4x on the apply phase for one-way SFTP→SFTP backups when the server admits the sessions; near-zero for local→SFTP (unchanged) and for two-way SFTP↔SFTP (still 1). Confidence: **medium-high** on the deadlock reasoning, **medium** on the throughput gain (bounded by server `MaxSessions` and sshd CPU).
- **Effort and risk:** small; one plan-direction check in `workers()`. Risk: if a copy's acquisition order ever changes, the deadlock returns; add a comment and a test that a mixed-direction plan stays at one worker. The existing `workers()` tests and `sessions.rs` tests cover the pool.
- **Measurement plan:** fixture `sftp-server` (or two), 100k-small-file one-way SFTP→SFTP sync at 1 vs 4 workers; record wall clock, requests/file, and pool clamp events. Add a unit test with a synthetic mixed-direction plan asserting `workers() == 1`.

### 7. Store the base as a sorted `Vec` and binary-search it

- **Category:** data structures
- **Evidence:** `crates/foldover-state/src/pairs.rs:353-375` — `PairStore::base` collects every row into a `BTreeMap<SyncPath, BaselineEntry>`, cloning each path out of the `BaseRow` owned `Vec<u8>` (`crates/foldover-db/src/database.rs:929-941`). `crates/foldover-engine/src/plan.rs:507-650` — `plan_resolved` iterates the base in path order with a peekable iterator and does `base.get`/`contains_key` lookups; the merge is a linear three-way walk over sorted maps. `BaselineEntry` holds two `EntryVersion`s (`crates/foldover-types/src/reconcile.rs:87-90`), each with two 32-byte digests.
- **Hypothesis:** the base is read once per run into a `BTreeMap`, then only iterated in order and probed by path. A sorted `Vec` of `(SyncPath, BaselineEntry)` with binary search has the same asymptotic lookups, a much smaller node overhead (no `BTreeMap` pointers/colors), better cache locality during the merge, and no second path copy. At 1M entries this is a meaningful memory and CPU saving on the prepare path.
- **Proposed change:** change `PairStore::base` to return a sorted `Vec<(SyncPath, BaselineEntry)>` (or a small `Base` newtype with `get`/`iter`), and adapt `plan_resolved`/`protect_*`/`unavailable`/`uncertain_absences` to its `get` (binary search) and ordered iteration. Keep the DB layer's `ORDER BY path` (`database.rs:931`) as the sort guarantee.
- **Expected impact:** removes the `BTreeMap` node overhead and one path clone per entry; estimated 1-3 s per 1M-entry prepare (the `db_read_100k` budget is 300 ms, so 10x scale is ~3 s, of which the map build is a fraction) and a lower peak RSS. Confidence: **medium** (the access pattern is verified; the timing is inferred from the budget).
- **Effort and risk:** medium; the return type is used across `foldover-engine` and tests. Risk: callers that rely on `BTreeMap`-specific APIs (`range`, `split_off`) must be adapted; the plan only needs ordered iteration and `get`. Existing `base_round_trips_and_is_bound_to_the_pair_revision` and plan tests cover the semantics.
- **Measurement plan:** run `cargo xtask bench-check` (`db_read_100k`) before/after; add a 1M-entry base-read bench and measure peak RSS with `/usr/bin/time -l` (or `getrusage`) during `PairRun::prepare`. Confirm the plan proptests still pass.

### 8. Cut peak memory with an arena/streaming tree representation

- **Category:** allocation and memory layout
- **Evidence:** `crates/foldover-endpoint/src/local.rs:1146-1165` buffers every entry of the tree in `entries: Vec<LocalEntry>` before versioning; `crates/foldover-endpoint/src/sftp.rs:489-543` buffers every listed entry as `(SyncPath, Attributes)` and then a second `reads` list; `crates/foldover-endpoint/src/local.rs:425-433` stores the whole observation in `BTreeMap<SyncPath, ObservedEntry>` (held per side in `PairRun`, `crates/foldover-engine/src/run.rs:653-668`); `plan.rs:62-65` stores a `PlanRow` per entry; `run.snapshot()` (`run.rs:925-942`) clones every entry again into a `BTreeMap` and a `Vec<SnapshotEntry>`. `SyncPath` is a heap `Vec<u8>` (`crates/foldover-types/src/sync_path.rs:11`), `ObservedEntry` holds an `EntryVersion` (two 32-byte digests) and a `Fingerprint` (heap `Vec` key), and `BaselineEntry` holds two `EntryVersion`s.
- **Hypothesis:** at 5M files the same path is stored in at least four places (listed buffer, observation map, plan rows, snapshot), each with its own heap allocation and map node. Peak RSS can reach multiple GB, causing swapping or allocation failure on the very workload this tool targets. The sibling passes cover allocation churn ([sftp-million-file-hot-paths.md](sftp-million-file-hot-paths.md) proposal 8, [sftp-million-file-run-costs.md](sftp-million-file-run-costs.md) proposal 8); this entry targets the duplicate path storage and the full-tree buffers themselves.
- **Proposed change:** store paths in a single arena (a `Vec<u8>` plus offsets, or a `bumpalo`-style allocator) and have `SyncPath` borrow from it for the duration of a run; or stream the listing into the version readers instead of materializing `listed`/`reads`, and let the snapshot encode directly from the observation. At minimum, drop the `reads` copy and iterate `listed` in place, and avoid the `snapshot()` `BTreeMap` by chaining the cache and observation iterators.
- **Expected impact:** a large reduction in peak RSS (potentially hundreds of MB to GB at 5M entries) and fewer allocations; wall-clock effect depends on whether the process is currently swapping. Confidence: **medium** on the memory sizes (derived from the struct layouts), **low-medium** on the wall-clock effect.
- **Effort and risk:** high; the arena lifetime must cover the plan, the observation, and the snapshot, and the public `SyncPath` API is used across the workspace. Risk: a borrow-checker fight or a subtle lifetime bug; the plan and snapshot tests are the safety net.
- **Measurement plan:** add a 1M-entry prepare bench and record peak RSS with `/usr/bin/time -l` or `getrusage` before/after; use a counting `#[global_allocator]` in a bench to count allocations per entry. Compare `db_snapshot_unchanged_100k` and `plan_100k_entries` medians.

### 9. Remove the extra copy in `write_chunks` and size the read buffer to the packet

- **Category:** allocation and memory layout / I/O and batching
- **Evidence:** `crates/foldover-net/src/sftp.rs:433-470` — `write_chunks` takes a `produce` closure that pushes chunks into an internal `buffer: Vec` (`:441-459`), copying each chunk, then `queue_write` sends `buffer` (`:471-500`). In the local→SFTP copy path, `source.push` reads a 64 KiB chunk from disk and calls the sink (`crates/foldover-endpoint/src/sftp/transfer.rs:505-528`), so every 32 KiB of file data is copied once into `buffer` before being written. `sftp.rs:209` — `output: BufReader::new(output)` uses the default 8 KiB capacity, while packets are up to 32 KiB (`CHUNK`, `:32`); `receive_until` (`:840-870`) allocates `vec![0; length]` per reply, and `request` (`:689-694`) allocates a packet `Vec` per request. `receive_for` (`:740-767`) does linear `stashed` scans, which become O(WINDOW²) if the window is raised as the sibling passes propose.
- **Hypothesis:** for large-file copies the extra 32 KiB memcpy is pure memory traffic; for all SFTP I/O the 8 KiB `BufReader` forces a second syscall per packet and the per-packet allocations churn the allocator. These are small per-byte costs that compound over millions of files and GiBs of data.
- **Proposed change:** let `write_chunks` accept a borrowed chunk (or write directly from the producer's buffer) instead of copying into an internal `Vec`; size the `BufReader` to at least `CHUNK + 64` (or use a reusable packet buffer for `receive_until`); and replace `stashed: VecDeque` with a `HashMap<u32, Vec<u8>>` if `WINDOW` is increased. Keep the `MAX_STASHED` bound and drain discipline.
- **Expected impact:** single-digit percentage off large-file copy CPU and a small reduction in syscalls/allocs across all SFTP I/O; near-zero for sub-32 KiB files. Confidence: **medium-low** (the copies and allocations are verified; the wall-clock effect is unprofiled).
- **Effort and risk:** small-medium; the `write_chunks` signature change touches `upload_on`, `write_new`, `create_lock_file`, and `stage_copy_on`. Risk: a borrow conflict where a producer holds a buffer across a call; mechanical to resolve. Existing wire tests cover the write path.
- **Measurement plan:** `cargo xtask bench-check` (`hash_64_mib`) plus a new `sftp_write_1gib` bench against the spawned `sftp-server`; count allocations with a global-allocator wrapper in a bench; measure large-file copy wall clock before/after.

## Requires approval (changes a correctness contract)

These ideas are not ranked because they weaken documented guarantees. They are listed so the trade-off is explicit.

- **Skipping the post-read `lstat` in `read_range_on`.** `crates/foldover-endpoint/src/sftp.rs:793-800` re-stats the file after reading to detect a concurrent edit that landed after the read. The read itself already enforces the expected size and detects short/overlong replies (`:783-791`), but the `lstat` closes the race window. Removing it would save one round trip per observed file (the sibling [sftp-million-file-db-apply-hot-paths.md](sftp-million-file-db-apply-hot-paths.md) proposal 2 pipelines it instead, which is safe); dropping it needs a product decision.
- **Stat-trust SFTP observation and stat-key verification.** Skipping the content re-read when the stat key matches, and verifying moves/replacements by stat key, reverse the documented invariant that "SFTP stat cannot prove a file unchanged" (`crates/foldover-endpoint/src/sftp/readers.rs:1-6`, `sftp.rs:469-472`). The sibling passes cover these in detail; they need an opt-in or a bounded re-hash schedule.
- **`synchronous = NORMAL` for the state database.** Covered by [sftp-million-file-run-costs.md](sftp-million-file-run-costs.md); it trades power-loss durability for commit throughput.
- **Parallel copies for two-way SFTP↔SFTP pairs.** The deadlock guard at `run.rs:1430-1442` exists for mixed-direction copies; proposal 6 only lifts it when the plan's copy directions are uniform.

## Open questions and unverified items

- **Nothing was executed or profiled.** No build, bench, test, or live SFTP run was performed in this session; every impact figure is a hypothesis. The code-structure facts and line numbers were read at the current checkout (`3fbb864`).
- **The workload shape is unknown.** The local-vs-SFTP split, the non-ASCII fraction, the changed fraction per run, and the average file size determine whether proposal 1/4 (local scan), 5 (respelling), 3 (read amplification), or 8 (memory) dominates. A `find | wc -l`, a sample of non-ASCII names, and a size histogram on the target tree would settle it.
- **Syscall counts are inferred from the code, not traced.** Proposals 1 and 4 should be confirmed with `dtruss`/`strace -c -f` on a 10k-file `observe_from` before implementation.
- **Server facts are unverified.** The target SFTP server's `MaxSessions`, READDIR batch size, and maximum accepted request size affect proposals 3, 5, 6, and 9. The spawned-`sftp-server` harness (`FOLDOVER_SFTP_SERVER`) is the stand-in.
- **The `listings` cache bound (`LISTED_FOLDERS` = 512) may limit proposal 5** on trees with many folders; the cache-clear behavior (`spelling.rs:155-158`) needs measurement before the cache-aware respelling is implemented.
- **The base `Vec` change (proposal 7) assumes the planner only needs ordered iteration and `get`.** A caller using `BTreeMap`-specific APIs would need adaptation; a quick `grep` for `base.` in `foldover-engine` should confirm this before implementation.
