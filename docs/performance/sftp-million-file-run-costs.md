# Performance proposals: end-to-end cost of million-file runs against a LAN SFTP server

Foldover is a macOS app built on a portable Rust workspace (`crates/`): `foldover-service` schedules runs, `foldover-engine` loads base state and snapshots, observes both endpoints, plans, then applies copies/archives on worker threads while the run thread journals and commits base updates in batches to a SQLite (`WAL`, `synchronous=FULL`) store. `foldover-endpoint` implements local/SFTP/peer endpoints; `foldover-net` speaks SFTP v3 over one `ssh -s sftp` subprocess per session (`CHUNK = 32 KiB`, `WINDOW = 16`, pipelined reads and writes, serial `copy_data`). The workload studied here is comparing and copying millions of documents to an SFTP server on the local network, measured by end-to-end run time. For that workload the cost model is dominated by **round trips per file and serialized phases**, not bandwidth: each SFTP file read costs ~4-5 round trips (plus a fixed 16-request read window), each staged write ~6-9, and the two side scans, the directory-listing pass, and the commit loop each serialize work that does not have to be serial. Proposals are ranked by expected reduction in end-to-end run time weighted by effort and risk. A sibling analysis exists at `docs/performance/lan-sftp-end-to-end-sync.md`; this one adds engine-side findings it does not cover (sequential side observation, unconditional preview, commit/identity batching internals, allocation churn) and classifies changes that weaken remote-change detection as requiring approval rather than as ordinary optimizations. Everything cited was verified by reading the source at commit `5be11da`; no live profile was taken, so every magnitude below is a hypothesis with an explicit confidence level.

## Ranked proposals

1. Raise SFTP concurrency to the 8-connection band PLAN.md §4.9 allows
2. Observe the two sides concurrently instead of left-then-right
3. Cap each SFTP read window at the listed file size
4. Parallelize SFTP directory listing and overlap it with file reads
5. Remove fixed per-file round trips on the SFTP write path
6. Amortize base commits and root-identity re-reads past `COMMIT_BATCH`
7. Make the unreviewed-run preview lazy
8. Reduce allocation churn across observe → plan → snapshot
9. Fan out local file versioning across workers
10. Raise `CHUNK`/`WINDOW` for bulk file transfer

---

### 1. Raise SFTP concurrency to the 8-connection band PLAN.md §4.9 allows

- **Category:** concurrency and parallelism
- **Evidence:** `crates/foldover-endpoint/src/sftp.rs:66-70` — `PARALLEL_COPIES = 4`, `SESSIONS = PARALLEL_COPIES + 1`. PLAN.md §4.9 specifies "network 4–8 connections". The same pool serves both observe readers (`observe_reads` → `self.workers()`, sftp.rs:597) and copy workers (`Copies::start`, `crates/foldover-engine/src/run/copies.rs:57-93`). `Sessions::acquire` already clamps the limit after three consecutive connection refusals and restores it after successes (`crates/foldover-endpoint/src/sftp/sessions.rs`), so a server that caps sessions degrades gracefully.
- **Hypothesis:** almost every SFTP operation is a fixed chain of sequential round trips (~4-5 per observed file, ~6-9 per copied file). With LAN RTT ≈ 0.2-1 ms the sessions are latency-bound, not bandwidth-bound, so throughput per phase scales nearly linearly with worker count until the server refuses connections or CPU saturates. Moving 4→8 workers should roughly halve the observe and apply phases for million-small-file runs.
- **Proposed change:** make `PARALLEL_COPIES`/`SESSIONS` per-pair configurable with default 8 (or derive from measured RTT); keep the SFTP↔SFTP forced-single-worker rule (`run.rs:1430-1441`) and the existing refusal clamp. Optionally multiplex several logical sessions over fewer SSH connections via `ControlMaster`/`ControlPath` so NAS `MaxStartups` limits are not hit — a larger follow-up.
- **Expected impact:** up to ~2x on observe and apply phases for million-small-file runs where the server admits the sessions; near-zero for single-large-file transfers. Confidence: **medium-high** (bounded by server session limits and sshd CPU).
- **Effort and risk:** small — a constant plus a config field; blast radius is session-count only. Risks: NAS `MaxStartups`/per-IP connection limits (clamped automatically), more `ssh` subprocesses (~1 MiB buffers each, `foldover-net/src/sftp.rs` `MAX_PACKET`), server-side load.
- **Measurement plan:** fixture `sftp-server` behind the latency relay used for ADR 0046's measurements (`crates/foldover-net/src/sftp/tests.rs` spawns a real `sftp-server`); run `observe_from` and a first-sync apply over a 100k-small-file tree at 4 vs 8 vs 12 workers; record wall clock, requests/file, and pool clamp events. Existing guard: `scan_10k_files` bench plus `cargo xtask bench-check`.

### 2. Observe the two sides concurrently instead of left-then-right

- **Category:** concurrency and parallelism
- **Evidence:** `crates/foldover-engine/src/run.rs:773-774` — `observe(Side::Left)` completes before `observe(Side::Right)` starts. The two endpoints are independent objects; `progress` is `&dyn RunProgress` and `control` is a shared callable, both already used from copy-worker threads (`run/copies.rs:198-225`). Endpoint opening (`SftpEndpoint::open`, sftp.rs:97-113, an SSH handshake plus probe `read_dir` each) is likewise sequential in `EndpointPair::open`.
- **Hypothesis:** the compare phase costs T_left + T_right serially, but a local↔SFTP pair spends most of T_right on the network while the local scan is CPU/disk-bound — the two do not contend for the same resource. Overlapping them removes min(T_left, T_right) ≈ the entire local scan from the critical path, and the same applies to two SFTP sides (different sessions). For a million-file local side at the `scan_10k_files` budget (~10k entries/s) that is ~100 s of scan plus per-file hashing of new/changed entries.
- **Proposed change:** run the two `observe_from` calls on two scoped threads sharing an atomic stop flag and the `RunProgress` sink (per-side `observed` labels already exist); join and merge results before `align_spellings` (run.rs:777-778). Requires `Observation` to be `Send` (it is data-only) and control to be shared by reference rather than `&mut` — the `Copies` machinery already demonstrates the pattern.
- **Expected impact:** removes the smaller side's scan time from every run — for local↔SFTP million-file pairs, an estimated 5-25% of compare-phase time depending on local tree size and changed fraction. Confidence: **high** on mechanism, **medium** on magnitude.
- **Effort and risk:** medium — mostly plumbing a shared control/progress into two scoped threads; no protocol or correctness change. Risk: a cancel must stop both (the shared `stop`/`AtomicBool` pattern handles it), and error ordering must stay deterministic (report left failure first, as today).
- **Measurement plan:** time `PairRun::prepare` on a pair with a 100k-file local tree and a fixture SFTP tree, before/after; assert both sides' `ObserveStep` counts interleave in a tracing shim. Also measure the two-endpoint open path if parallelized.

### 3. Cap each SFTP read window at the listed file size

- **Category:** I/O and batching
- **Evidence:** `Session::read_from` (`crates/foldover-net/src/sftp.rs:347-365`) unconditionally sends `WINDOW` (16, line ~35) `READ` requests before consuming any reply. For a file smaller than `WINDOW × CHUNK` (512 KiB — most documents), 15 of 16 requests answer EOF or short reads and are discarded (`short = data.len() < CHUNK`, line 407). `read_small_on` (`crates/foldover-endpoint/src/sftp.rs:1648-1669`) calls `read_all` → `read_from`, so even the 64-byte identity file costs OPEN + 16 READs + CLOSE. Observers know each file's size — `read_range_on` (sftp.rs:750-806) has `expected.size` from the listing attributes.
- **Hypothesis:** for a sub-512 KiB file the client sends ~19-20 packets where ~5 suffice (OPEN + ⌈size/32KiB⌉ READs + CLOSE + post-LSTAT): ~4x fewer requests per file, less ssh encrypt/decrypt work, less server request processing, and a shorter drain tail per file. At a million files this is ~15M avoided requests across the observe phase alone; the same waste recurs for every `read_small` (identity checks, canary reads) and every small `copy_data` transfer.
- **Proposed change:** add `read_range(handle, offset, len)` (or a `read_up_to`) that sends only `min(WINDOW, ceil(remaining/CHUNK))` requests per round; route `version_on`/`read_range_on`, `read_small_on`, and `copy_data` through it. Keep the existing EOF/short-read validation — it still guards servers that truncate.
- **Expected impact:** ~4x fewer READ packets per small file; observe-phase packet count drops roughly from ~19-20 to ~5 per file (latency per file only drops where the discarded replies would have added a round trip — bounded gains, mostly server/ssh CPU and tail latency). Estimated 10-30% of observe-phase time for million-small-file scans. Confidence: **high** that the waste occurs, **medium** on magnitude.
- **Effort and risk:** small-medium — one new window-bounded read loop in `foldover-net`, call-site swaps in the endpoint; no semantics change (fewer requests, same data). Risk: subtle EOF/short-read edge cases — covered by existing wire tests plus a size-boundary test.
- **Measurement plan:** instrument `Session::send_for`/`receive_for` (or a packet-counting shim around `Session::request`) and count requests during `observe_from` over a 10k-file fixture tree; compare request totals and wall clock before/after. Add a Criterion bench reading 1 KiB and 500 KiB files via the real `sftp-server`.

### 4. Parallelize SFTP directory listing and overlap it with file reads

- **Category:** concurrency and parallelism
- **Evidence:** `observe_reporting` (`crates/foldover-endpoint/src/sftp.rs:493-544`) performs a single-session, depth-first `READDIR` loop over the whole tree before any file read is queued (reads start only at line 569). Each `Session::read_dir` (`foldover-net/src/sftp.rs:267-301`) issues `OPENDIR`, then strictly sequential `READDIR` requests — one round trip per reply batch — then `CLOSE`. File reads already fan out over pooled sessions (`readers::read_each`, `crates/foldover-endpoint/src/sftp/readers.rs`).
- **Hypothesis:** a million-file tree typically means tens of thousands of directories; at ~1.5-2 round trips each on one session the listing phase alone is tens of thousands of serial RTTs (tens of seconds on a LAN), and nothing overlaps it with the read phase that follows. Pipelining `READDIR` on each directory handle and spreading directory traversal across the session pool — feeding discovered files straight into `read_each`'s work queue — removes most of that front-loaded latency.
- **Proposed change:** (a) inside `read_dir`, keep up to `WINDOW` `READDIR`s in flight per handle using the same `pending`/`VecDeque` pattern as `read_from`, stopping on EOF and draining the rest; (b) restructure `observe_reporting` so discovered directories become work items on the same pool the readers use (directories settle before their files' results are recorded, preserving the "folders first" ordering the code relies on at sftp.rs:545-546,623-628). Part (a) alone is the cheap, self-contained half.
- **Expected impact:** removes ~O(directories) serial RTTs from the critical path; for wide/deep trees plausibly 10-40% of observe-phase time, near-nil for flat shallow trees. Confidence: **medium-high** for the mechanism, **low-medium** on end-to-end magnitude (directory fraction is workload-dependent).
- **Effort and risk:** (a) small, contained in `read_dir`; (b) medium — a pipelined producer/consumer observe needs the same record-on-run-thread discipline as `read_each`, plus deterministic issue ordering. Risk: desynchronized replies on error — the session already bounds/drains stashed replies (`MAX_STASHED`, sftp.rs:~46).
- **Measurement plan:** count `READDIR` requests and wall time listing a 100k-entry flat dir and a 10k-dir nested tree on the fixture server through the latency relay, before/after (a); end-to-end `observe_from` time for (b). The `scan_10k_files` bench does not cover SFTP — add an equivalent observe bench or reuse the ADR 0046 harness.

### 5. Remove fixed per-file round trips on the SFTP write path

- **Category:** redundant work and caching
- **Evidence:** placing one staged file issues, in order: `set_metadata_on` → `session.lstat(remote)` (sftp.rs:948), then `staged_version_on` → `session.lstat(remote)` again (sftp.rs:928) — two LSTATs of the same staged file moments apart — then `place_on` → `lookup_on` LSTAT + `listed_on` + `set_aside_on` → `make_directories_on` (sftp.rs:1606-1641), which walks every path component with `make_directory` + fallback `lstat`, ignoring the `listings` cache that already records folders seen or created this run (`listings` field, sftp.rs:87-93; `note_added` calls e.g. sftp.rs:990, 908). `check_roots`'s per-batch `identity()` (`read_small`, sftp.rs:315-316 → 1648-1669) is a further fixed cost covered by proposal 6.
- **Hypothesis:** ~1-3 of the ~6-9 round trips per created/replaced file are redundant: the second staged LSTAT can reuse the first result (or the `set_attributes` path can return post-state), and `make_directories_on` can skip components the `listings` cache already proves exist this run. For a million creates across 4-8 workers this is ~1-3M requests removed.
- **Proposed change:** have `set_metadata_on` return the attributes it fetched (and re-stat only when it actually called `set_attributes`), pass them into `staged_version_on`; consult `listings` in `make_directories_on`, marking components created this run via `note_added` and falling back to the network walk on a cache miss or `Dirty` entry (`spelling.rs`'s `Dirty` discipline already exists for exactly this). Separately, for `Propagation::Sync` permissions send `SETSTAT` unconditionally with the wanted mode instead of LSTAT-then-maybe-SETSTAT (same or fewer RTTs, same result).
- **Expected impact:** ~1-3 RTTs saved per created/replaced file — an estimated 15-35% of apply-phase request latency on create/replace-heavy runs to SFTP. Confidence: **medium-high**.
- **Effort and risk:** medium — the LSTAT reuse is easy; the cache-aware `make_directories_on` must respect `Dirty` marking and cross-session visibility (another session's mutation can invalidate the cache — the existing invalidation hooks already handle the endpoint's own mutations; external changes surface as the same failures they cause today). Risk of a wrong-spelling write if the cache lies — bounded by `Dirty` discipline and the existing post-place `attributes_on` check (sftp.rs:1070).
- **Measurement plan:** shim `Session::request` to count packets; run a 10k-file create run and a 10k-file replace run against the fixture server before/after; compare requests-per-file and wall clock. `DestinationChanged` rates in `crates/foldover-endpoint/src/sftp/tests.rs` must be unchanged.

### 6. Amortize base commits and root-identity re-reads past `COMMIT_BATCH`

- **Category:** I/O and batching
- **Evidence:** `COMMIT_BATCH = 256` (`crates/foldover-engine/src/run.rs:52`). Every 256 plan rows the run calls `check_roots` (run.rs:1235-1237 → 1378-1397), which calls `identity()` per recorded side — on SFTP that is `read_small` → OPEN + `read_from`'s 16-READ window + CLOSE ≈ 18 requests per side, ~36 per batch (~140k requests for a million-row run). Separately, `commit_batch` (run.rs:1256-1258, closure at 1177-1187) issues one SQLite transaction per 256 base/journal rows under `synchronous=FULL` (`crates/foldover-db/src/database.rs:646-651`) — ~3900 fsync'd transactions for a million-row run, each holding `engine.lock()` (`commit` closure, `crates/foldover-service/src/sync.rs:918+`), which serializes copy workers behind the run thread.
- **Hypothesis:** both per-batch costs are protection mechanisms whose frequency, not existence, is the expense: a million-row run pays ~4k fsyncs and ~140k identity-check packets for a 64-byte file and a bounded-redo guarantee. Larger batches (or time-based intervals) keep the same crash semantics — `run.rs`'s own comment states batching limits redo work after a crash — while cutting per-row overhead ~8-16x.
- **Proposed change:** raise `COMMIT_BATCH` (e.g. 2048-8192) and/or make the root check time-based (`every N seconds` rather than every batch, with a per-batch minimum row count); proposal 3's size-bounded reads separately shrink each identity read to ~5 requests. Keep the guarantee: batches still commit before archives' journal rows are spent and on any error path (run.rs:1239-1241, 1264, 1275).
- **Expected impact:** ~4k→~250-500 fsync transactions (~2-8 s on typical SSDs) and ~140k→~9-18k requests for a million-row run; also shortens the periodic stall where all workers wait on the run thread. Estimated a few percent to ~10% of apply-phase end-to-end time on change-heavy runs. Confidence: **high** the requests/fsyncs happen, **medium** on magnitude.
- **Effort and risk:** small — a constant plus an interval check; blast radius is crash-redo volume (bounded extra redo on crash — exactly the trade-off the constant already encodes) and later detection of a lost/remounted root (bounded by the time-based check). Risk: very large batches lengthen redo work after a crash; keep the cap modest.
- **Measurement plan:** instrument `commit_batch` invocations, `check_roots` calls, and `read_small_on` request counts for a 100k-change run at batch sizes 256/2048/8192; measure `PRAGMA synchronous` fsync cost directly by timing `commit_run` batches in `foldover-db` tests; existing `db_commit_100k` bench (budget 1000 ms) covers the transaction path.

### 7. Make the unreviewed-run preview lazy

- **Category:** redundant work and caching
- **Evidence:** `Work::Run` calls `run.preview()` unconditionally (`crates/foldover-service/src/sync.rs:947-948`). The result is used only to compute `reviewed` (954-956) or to build a `NeedsApproval` response (957-964); on the common path — no held review, no token, `!approval.approves_anything()` — the whole `Preview` is built and dropped. `Preview` clones every changed row's path and versions and hashes the plan into a token (`Reviewed::from(&planned)`).
- **Hypothesis:** for a run with N changes the preview is O(N) allocations plus an O(N) BLAKE3 pass — hundreds of thousands to millions of `PreviewItem` clones on a million-change plan — paid even when nothing can approve or review. `Work::Scheduled` already skips it (sync.rs:975); the interactive happy path can too.
- **Proposed change:** compute `planned` lazily: when `held` is `None` and `token` is `None` and `!approval.approves_anything()`, skip `preview()` entirely and go straight to `execute` (which itself calls `self.preview()` on the `NeedsApproval` paths it can hit). When a held preview exists or a token/approval is presented, build it as today.
- **Expected impact:** removes an O(changes) clone+hash pass from every unreviewed interactive run — a few seconds plus a large memory spike on million-change plans; zero on small plans. Confidence: **high** on mechanism, **medium** on magnitude.
- **Effort and risk:** small — reorder an evaluation in `sync.rs`; no behavior change (the `reviewed` outcome is identical when no preview/token exists to compare against). Risk: a path that needs `planned` earlier than expected — audit the `held`/`token`/`approval` matrix in tests.
- **Measurement plan:** time `Work::Run` end-to-end on a prepared run with a large plan and no approval inputs (service-level test or instrumented `foldover-cli` sync); count `preview()` calls via a counter or tracing span before/after.

### 8. Reduce allocation churn across observe → plan → snapshot

- **Category:** allocation and memory layout
- **Evidence:** (a) `Observation::versions()` (`crates/foldover-endpoint/src/local.rs:584-589`) builds a fresh `BTreeMap<SyncPath, EntryVersion>` per side per run — ~1M cloned keys + inserts each — purely to hand the planner a borrowed view. (b) `plan_resolved` (`crates/foldover-engine/src/plan.rs`) runs `validate_tree` three times (523-525), the merge loop (527-597), `settle_folder_choices`, `skip_branches`, `mark_name_clashes` (which allocates a `name_key` `Vec<u8>` per row at 362-368 — plus NFC/lowercase `String` work in `name_key`, 421-439 — and runs whenever either side is case-insensitive or normalized, i.e. any local↔SFTP pair), and the ancestor-block walk (605-625) that calls `path.parent()` — an owned `SyncPath` clone — once per ancestor per row. (c) `run.snapshot()` + `store_snapshot` (`crates/foldover-service/src/sync.rs:909-915`, `configuration.rs`) re-encode every entry — path bytes, fingerprint `to_bytes` (local.rs:355-366), version encode — into owned `Vec`s per entry per side, before `replace_snapshot`'s diff-write discards unchanged rows. (d) `remote()`/`stat_key`/`read_dir` allocate a `Vec` per path conversion, per stat compare, and per listed name (`foldover-net/src/sftp.rs:284`), and `receive_until` allocates `vec![0; length]` per reply packet.
- **Hypothesis:** at a million entries these passes turn into several million small heap allocations and copies per run — seconds of CPU plus a large memory high-water mark — without changing any output. Most are replaceable by borrowed views, cached keys, or reused buffers.
- **Proposed change:** (a) let the planner iterate `&BTreeMap<SyncPath, ObservedEntry>` via a value-mapping adapter (or accept an iterator of `(path, version)` pairs) instead of materializing `versions()` maps; (b) compute `name_key` once per row into the `PlanRow` (or a parallel `Vec`) and iterate path components without cloning `parent()` chains; (c) stream snapshot rows (encode straight into prepared-statement bindings inside `replace_snapshot`'s diff cursor) rather than materializing `Vec<SnapshotEntry>` then `Vec<SnapshotRow>`; (d) grow-only reusable buffers for `remote()` joins and packet receive, and an arena/`SmallVec` for `read_dir` names.
- **Expected impact:** several hundred ms to a few seconds of CPU plus reduced peak RSS per run at million-entry scale — small but compounding, and it makes every other win more visible. Confidence: **medium**.
- **Effort and risk:** medium-large — many small changes across four crates; each is mechanical but the planner's `BTreeMap` API is a public-ish boundary (`plan_candidates` signature, plan.rs:461-469). Risk: subtle behavior drift in dedup/ordering — the plan is exhaustively tested (`plan.rs` tests + simulation seeds).
- **Measurement plan:** `plan_100k_entries`, `db_snapshot_unchanged_100k`, `db_snapshot_rewrite_100k` Criterion benches via `cargo xtask bench-check` before/after each sub-change; add an allocation counter (e.g. `#[global_allocator]` wrapper in a bench) to quantify allocs/entry.

### 9. Fan out local file versioning across workers

- **Category:** concurrency and parallelism
- **Evidence:** local observe serializes per-entry work on the scan thread: `entry_version` (`crates/foldover-endpoint/src/local.rs:1233-1249`) reads extended metadata and calls `hash_file` (`crates/foldover-fs/src/root/content.rs`) for every file not proven unchanged — per file: open + metadata checks + 64 KiB-buffered BLAKE3 + post-read checks. `local.rs:743` already advertises `workers()` (medium-dependent), but the fan-out used for SFTP reads (`readers::read_each`) is not used on the local path — unchanged-stat hits are reused (local.rs:1198-1204) yet every first-sync and every changed file is hashed serially.
- **Hypothesis:** on a first sync (or a large changed set) the local side hashes every document single-threaded; on an SSD with BLAKE3, worker fan-out of ~4 would overlap syscall latency and hash compute for roughly a 2-4x local-scan speedup. This currently hides inside proposal 2's overlap but becomes the critical path once observe is parallel.
- **Proposed change:** reuse the `read_each` pattern for local files: stat/fingerprint reuse stays on the scan thread (it must update `observation` deterministically); files needing `entry_version` go to a bounded worker pool over `Root::try_clone` handles, results recorded in listed order on the run thread.
- **Expected impact:** ~2-4x on the local hash portion of first-sync and high-churn scans — for a million changed small documents, minutes to under a minute; near-nil on steady-state scans where stat reuse dominates. Confidence: **medium** (syscall-bound small files may scale less than 4x).
- **Effort and risk:** medium — mirrors `readers.rs`; must keep `Observation` recording single-threaded and preserve `at_scan` metadata discipline (`local.rs:1173-1196`). Risk: fd pressure (bounded workers), changed-file detection semantics unchanged since workers still use `open_observed_file` checks.
- **Measurement plan:** extend `scan_10k_files` with a "changed files" variant (or a new `scan_hash_10k_files` bench) measuring observe over 10k previously-unseen files; compare serial vs 4 workers on SSD.

### 10. Raise `CHUNK`/`WINDOW` for bulk file transfer

- **Category:** I/O and batching
- **Evidence:** `crates/foldover-net/src/sftp.rs` — `CHUNK = 32 * 1024` ("every server accepts 32 KiB") and `WINDOW = 16`, capping in-flight data at 512 KiB per session; `MAX_PACKET` already tolerates 1 MiB replies. Streaming paths are already pipelined (`read_from` 347-365, `write_chunks`/`queue_write`), so per-session throughput ≈ `WINDOW × CHUNK / RTT`. `copy_data` (server-side copies, ~496-551) is additionally serial: one READ then one WRITE per 32 KiB chunk, ~2 RTTs each.
- **Hypothesis:** for multi-MiB files, 512 KiB in flight per session caps throughput and quadruples request/syscall counts versus a 128-256 KiB chunk; OpenSSH's `sftp-server` accepts read/write requests well above 32 KiB. The serial `copy_data` halves achievable throughput again on server-side copies (Put Back / undo).
- **Proposed change:** raise `CHUNK` to 128-256 KiB with negotiated fallback to 32 KiB on `SSH_FX_FAILURE` (the existing oversized-reply guard, sftp.rs:~536, already covers reads); size `WINDOW` for a bounded in-flight byte count (e.g. 2-4 MiB). Pipeline `copy_data` (interleave a bounded window of READs and WRITEs, honoring the "bounded requests on one session" deadlock constraint noted in `run.rs:1427-1429` — safest on two pooled sessions).
- **Expected impact:** up to ~3-6x per-session throughput on multi-MiB files; negligible for the small-document case (files under one chunk). Confidence: **medium** — server-dependent; measure against the real target servers.
- **Effort and risk:** small for the constants plus fallback; medium for `copy_data` pipelining. Risks: non-OpenSSH servers refusing large requests (mitigated by fallback), larger per-packet buffers (already bounded by `MAX_PACKET`), and request-ordering deadlocks if `copy_data` pipelines within a single stalled session — keep the one-session deadlock invariant or use two sessions.
- **Measurement plan:** fixture server — time 1 GiB up/down at (32 KiB, 16), (128 KiB, 32), (256 KiB, 32) and `copy_data` serial vs pipelined; also re-run `hash_64_mib` (budget 60 ms) since `HASH_BUFFER_BYTES` is a related constant on the local side.

## Requires approval (changes a correctness contract)

The largest possible win for this workload deliberately is not a free optimization: Foldover re-reads every remote file because SFTP stat fields (whole-second mtime, no inode/file-ID) cannot prove a file unchanged — `crates/foldover-endpoint/src/sftp/readers.rs` states this directly, and `observe_entry` computes the version **before** consulting `previous` (sftp.rs:642 vs 647-652, with the comment "SFTP versions are never reused unread", line 646). The same guarantee is paid again in `verified_at_on` (sftp.rs:823-837), which re-reads and re-hashes a file before every move, archive, or replacement. Weakening these checks trades correctness for speed, so they need an explicit product decision:

- **Opt-in stat-trust SFTP observation.** Skip the content re-read when `(size, mtime, mode, owner)` equals the stored fingerprint (`Fingerprint::from_key`/`same_stat`, local.rs:317-328) and the observation is fresh enough — mirroring the local `proves_unchanged`/`RACY_WINDOW`/`REREAD` machinery (local.rs:283-346, 1198-1204). Impact: the observe phase of a steady-state million-file sync drops from "download every byte" to "listing only" — plausibly an order of magnitude — at the cost of missing remote edits that preserve the whole stat tuple within the window. Confidence: **high** on mechanism and magnitude; the missed-edit risk is real for adversarial or coarse-mtime (1 s) servers. Could be narrowed: stat-trust only when the server advertises `check-file`-style digest extensions, nanosecond mtimes, or a monotonic file-ID.
- **Stat-key verification for moves/archives/replacements.** Same trade applied to `verified_at_on` callers (`move_entry`, `remove`, `receiving_on` with `Expected::Present`, `crates/foldover-endpoint/src/sftp/transfer.rs:419-444`): compare the expected stat key instead of re-reading content. Saves a full download per moved/archived/replaced file; same missed-edit risk class.
- **`synchronous=NORMAL` for the state DB.** Would cut each `commit_batch` fsync to a WAL write; WAL stays crash-safe for app crashes but a power loss could drop committed batches — the run would re-plan already-written files and fix itself, though base/journal consistency reasoning gets subtler. Only worth it if proposal 6's batching does not suffice.

## Open questions and unverified items

- **No live profile exists.** All magnitudes above are hypotheses from reading the source; the measured facts are the code structure itself and ADR 0046's published numbers (100k-entry snapshot/poll/archive/SFTP-read benchmarks on a 5 ms-latency relay). A real run against the target NAS class is the first measurement to take.
- **Round-trip counts per file are inferred, not counted.** ~19-20 requests per observed small file and ~6-9 per created file are derived from the call chains; a packet-counting shim around `Session::request`/`send_for` would confirm exact totals — several measurement plans above depend on it.
- **LAN RTT and server type are unknown.** All rankings assume ~0.2-1 ms RTT and OpenSSH `sftp-server` behavior; a slower NAS, higher latency, or a non-OpenSSH server reshuffles proposals 1, 3, and 10.
- **`Endpoint::observe` → `Observation` recording order under parallel observation.** Whether `align_spellings`/`unavailable` (run.rs:777-813) tolerate results arriving interleaved is assumed but not exercised — the merge step must still see complete per-side maps.
- **Whether the engine lock or copy workers bound commit throughput.** `commit_batch` runs under `engine.lock()` while workers wait in `collect`/`finish`; the true serialization cost needs an instrumented run, not just code reading.
- **Snapshot persistence cost at million-entry scale** — `run.snapshot()` + `replace_snapshot` per side per run is estimated from the encoding code and the 100k budgets (`db_snapshot_*`), not measured at 10x scale.
- **SSH multiplexing feasibility.** `ControlMaster`/`ControlPath` support depends on how `Session::connect` builds the `ssh` command line (`foldover-net/src/sftp.rs` `Command` construction) — not fully traced here; whether a single TCP connection can carry enough channels for 8+ workers needs the server's `MaxSessions`/`MaxStartups` values from the real target.
- **Whether stat-trust modes are product-acceptable** is explicitly out of scope — it changes the "SFTP stat cannot prove unchanged" invariant the codebase documents as deliberate (readers.rs header comment, ADR 0046).
